# 租约模型

## 1. 概念

| 概念 | 是什么 |
|---|---|
| Workspace | 本机上登记给 tcasd 的一组目录。通常是一个，也可以是几个不在一起的，例如项目的主目录加上并排的后端目录和网站目录 |
| 根 | workspace 里的一个目录。可以是一个 git 检出，也可以是装着几个检出的目录 |
| 仓库 | 某个根里的一个 git 检出。文件属于哪个仓库由它所在的位置决定，见第 3 节 |
| 会话 | 一个 harness 会话，以 harness 自己的会话 ID 标识。子 agent 和父会话是同一个会话 |
| 租约 | 某个会话对一个文件或一个目录的独占写权限 |
| 用户 | 不带会话身份运行 `tcas` 的人。不受租约约束，可以强制操作。会话能做哪些管理操作见 [daemon-and-cli.md](daemon-and-cli.md) 第 5 节 |

**读不受限。** 租约只管写。

## 2. 数据结构

```ts
interface Workspace {
  id: string                    // 短 ID
  name: string                  // 默认取第一个根的目录名
  roots: Root[]                 // 一个或多个，互不包含。见第 3 节
  mode: 'auto' | 'strict'
  openedBy: 'user' | SessionId
}

interface Root {
  name: string                  // 默认是目录名，重名时加序号。只有一个根时不显示
  path: string                  // 规范化后的绝对路径
  caseInsensitive: boolean      // 所在卷是否不区分大小写，加进来时探测
  addedBy: 'user' | SessionId
}

interface Repo {                // 某个根里的一个 git 检出，自动发现，见第 3 节
  workspace: WorkspaceId
  root: string                  // 所在的根的名字
  dir: string                   // 相对这个根；根本身就是检出时为 ""
  kind: 'repo' | 'submodule' | 'worktree'
  commonDir: string             // 所属仓库的 git 目录。主检出和它的 worktree 相同
  lastBranch?: string           // 上次看到的分支，用来发现分支变化
}

interface Session {
  id: string                    // "<harness>:<原生会话 ID>"，如 "claude:79583356-…"
  harness: 'claude' | 'agy' | 'codex'
  state: 'active' | 'idle' | 'ended'
  pid?: number                  // harness 进程
  pidStartedAt?: Time           // 和 pid 一起判断进程是否还是同一个
  cwd: string
  title?: string                // 第一条用户消息的前 80 个字符。只给用户看，不给别的会话看（第 5 节「brief」）
  brief?: string                // 这个会话在做什么，一句话。给别的会话看
  startedAt: Time
  lastSeenAt: Time
  endedAt?: Time
}

interface Lease {
  workspace: WorkspaceId
  root: string                  // 所在的根的名字
  path: string                  // 相对这个根，用 "/" 分隔
  isPrefix: boolean             // true 表示目录租约，覆盖目录下的所有路径，见第 4 节
  session: SessionId
  state: 'active' | 'orphaned'
  source: 'edit' | 'bash' | 'wait' | 'cli' | 'grant'
  brief?: string                // 申请这条租约时写的 brief；没写时显示会话的 brief
  acquiredAt: Time
  touchedAt: Time               // 持有者最近一次用到它的时间，见第 6 节「期限」
  committedAt?: Time            // 持有者最近一次提交这条路径（目录租约：它下面的路径）的时间，见第 6 节「提交过的显式租约」
}
```

`source` 决定释放规则（第 6 节）：

| source | 怎么来的 | 类别 |
|---|---|---|
| `edit` | 编辑工具第一次改这个文件时自动取得 | 隐式 |
| `bash` | Bash 调用后对账，发现本会话改了一个没人持有的路径 | 隐式 |
| `wait` | agent 运行 `tcas lease wait`，等到之后授予（第 7 节） | 等来的 |
| `cli` | agent 运行 `tcas lease acquire` | 显式 |
| `grant` | 用户运行 `tcas lease grant` 发给某个会话 | 显式 |

隐式租约跟着文件的未提交改动走。显式租约跟着会话的意图走，路径干净时也保留，但有空闲期限：持有者超过 30 分钟没用到它，就可以让出；持有者提交过它、而且这一轮已经结束时，也可以让出。等来的租约介于两者之间：授予后保留 10 分钟（等到的那一刻文件还没改），持有者提交后释放。期限见第 6 节。目录租约不论来源都按显式处理（第 4 节）。

## 3. 路径

所有判定之前先把路径规范化：

1. 相对路径按 hook 输入里的 `cwd`（命令行则按当前目录）转成绝对路径。
2. 解析父目录的符号链接，最后一级不解析；父目录还不存在时（新建文件到新目录），解析存在的最近一级，再接上其余部分。实测 hook 给出的路径已经解析过（`/tmp/…` 变成 `/private/tmp/…`），workspace 的根也必须按同样的方式存，否则前缀比较对不上。
3. 路径在豁免的目录里（见下面的「豁免」）：不归 tcasd 管，一律放行，到此为止。
4. 找到它所属的根：目录包含这条路径的那个。根之间不能互相包含，不管是不是同一个 workspace 的，所以最多一个。不在任何根里的路径同样不归 tcasd 管，一律放行。
5. 转成相对这个根的路径，租约里存的就是它。`caseInsensitive` 的根里，这一步和上一步的比较都不区分大小写（macOS 的卷默认不区分，hook 给出的大小写可能和登记的根不同）。
6. 找到它所属的仓库：从文件所在目录往上，第一个含有 `.git` 的目录，找到所在的根为止。`.git` 可以是目录，也可以是文件（链接的 worktree 和子模块里是文件）。git 查询在这个检出里做。
7. 路径在这个仓库里被 git 排除（见下面的「豁免」），或者在检出的 git 目录里（`.git/` 下面）：不归 tcasd 管，一律放行。git 目录里的文件要单独判断：实测 `git check-ignore` 不认为它们被排除，`git status` 也从不列出它们，不单独处理的话会被当成永远干净的被跟踪文件。

**路径怎么写、怎么显示**

- 给命令的路径相对当前目录，也可以写绝对路径。
- tcas 显示的路径：workspace 只有一个根时相对这个根，如 `web/src/app.ts`；有几个根时前面带根的名字，如 `app-backend/src/user.ts`。
- tcas 给出的可以直接运行的命令（等待的命令、建议的申请命令）里，路径一律写成从读它的那个会话的当前目录能用的形式，如 `../app-backend/src/user.ts`。

### 一个 workspace，几个目录

一个项目的代码常常不在一个目录下：会话都从主目录启动，agent 也会去改并排的后端目录、网站目录。把这些目录放进同一个 workspace：

```
$ cd ~/Code/app && tcas workspace open
$ tcas workspace add ../app-backend ../app-website
```

每个目录是 workspace 的一个根。

- **所有规则在几个根之间是通的。** 租约、等待、brief、通知、`tcas status` 覆盖整个 workspace；一次申请可以同时包含几个根里的路径；`tcas commit` 在涉及的每个仓库各提交一次。
- **Bash 的对账覆盖所有的根。** 会话在主目录里用一条命令改了后端目录的文件，照样被发现（[harness.md](harness.md) 第 5 节）。命令护栏和 git 钩子在每个根的仓库里都生效。
- **会话属于哪个 workspace**：它的当前目录在某个根里，或者它在里面持有租约。
- 几个目录正好并排在同一个上级目录下，而且那里没有别的不相干的仓库时，直接打开上级目录也可以，效果相同（见下面的「多个仓库」）。

**不要分开打开成几个 workspace。** 那样每个文件的互斥仍然成立，但一个 workspace 里的会话用 Bash 改了另一个 workspace 的文件不会被对账发现，状态和通知也各看各的。

**改到了 workspace 外面**

会话的当前目录在 workspace 里，却用编辑工具改了外面某个 git 检出里的文件。tcas 不拦，记下来，并且：

- 每个（会话，检出）提示一次：这个目录不受管理，别的会话在这里的改动不会和你协调；要管起来就运行 `tcas workspace add <目录>`（[harness.md](harness.md) 第 6 节）。
- `tcas status` 里列出这些目录、被改了几次，以及可以直接运行的命令。

不自动加进来：加一个目录要给里面的仓库装上 git 钩子，这一步要有人同意。会话运行 `tcas workspace add` 时由 harness 的权限规则决定是否放行（[daemon-and-cli.md](daemon-and-cli.md) 第 5 节）。

只看得到编辑工具的改动，Bash 对 workspace 外面的写入看不到。不在任何 git 检出里的路径不算，豁免目录里的也不算（哪怕那里有 git 检出）。

### 豁免

有两类路径 tcas 一概不管：不发租约、不拦截、不对账、不提示。

| | 是什么 | 什么时候判断 |
|---|---|---|
| 豁免的目录 | 临时目录、工具自己的目录、用户配置的目录 | 在所有判定之前，按绝对路径（上面的第 3 步） |
| 被 git 排除的路径 | 路径所属的仓库里，git 不跟踪也不会跟踪的文件：构建产物、依赖目录、缓存、本地的环境文件 | 找到所属的仓库之后（上面的第 7 步） |

另有一种按文件名模式的 `unmanaged`，用在被跟踪但不想发租约的文件上（如 lockfile），见本小节末尾。

**豁免的目录**

这些地方除了不管之外，也不能当成 workspace 打开。

| 来源 | 内容 |
|---|---|
| 内置：系统的临时目录 | `/tmp`、`/var/tmp`、`$TMPDIR`，以及它们解析符号链接之后的位置。macOS 上是 `/private/tmp`、`/private/var/tmp`、`/private/var/folders/…/T`（实测），Linux 上另有 `/dev/shm` |
| 内置：tcas 自己的目录 | `~/.tcas` |
| 内置：harness 自己的目录 | `~/.claude`、`~/.gemini`、`~/.codex`。会话的记录、计划、记忆、后台任务的输出都在这里或临时目录里（实测 Claude Code 把后台任务的输出放在 `/tmp/claude-<uid>/…`，AGY 把会话记录、artifact、scratch 和后台任务日志放在 `~/.gemini/antigravity-cli/brain/<会话>/…`） |
| 用户添加：全局 | `~/.tcas/config.toml` 的 `[exempt] paths`，写绝对路径或以 `~` 开头的路径 |
| 用户添加：按 workspace | `.tcas.toml` 的 `exempt`，相对它所在的根，只对根里面的目录有效 |

为什么要单独有这一条，而不是靠「不在任何 workspace 里」：

- **临时目录里的 git 检出不该被提示。** 脚本和测试经常在 `/tmp` 里建一次性的仓库。没有豁免的话，会话每改一个这样的仓库都会收到「加进 workspace」的提示（上面的「改到了 workspace 外面」）。
- **不能被管起来。** `tcas workspace open /tmp` 一类的命令会被拒绝，不管是用户还是会话运行的。
- **根里面也可以划出不管的目录。** 例如一个放草稿、没有被 git 排除的目录。

规则：

- **匹配的是规范化之后的绝对路径。** `/tmp/x` 和 `/private/tmp/x` 是同一个地方，两种写法都认。
- **豁免目录不能和 workspace 的根重叠到整个根。** 要打开的目录在全局的豁免目录里面：拒绝，说明是哪一条，以及不想豁免时怎么去掉。根里面的一个子目录可以豁免。
- **不能申请豁免目录的租约。** 申请的路径在豁免目录里时直接说明它不归 tcas 管，不记租约。目录租约覆盖的范围里有豁免的子目录时，那个子目录照样不管。
- **内置的可以关掉**：`[exempt] builtin = false`。之后临时目录和别的目录一样，可以被打开成 workspace。
- **只有用户能改豁免列表。** 全局的在 `~/.tcas` 里，这个目录本身是豁免的，但 tcas 对它另有一条规则：会话用编辑工具或认得出的 Bash 命令去改 `~/.tcas` 里的文件会被拒绝（[harness.md](harness.md) 第 4 节）。按 workspace 的在 `.tcas.toml` 里，同样只有用户能改：会话改根目录和各仓库根目录下的 `.tcas.toml`（tcas 读的就是这几份）会被拒绝，否则被护栏挡住的会话可以顺手把护栏关掉。
- 路径有没有落在豁免目录里，`tcas hook` 自己就能判断，不连 tcasd。

**被 git 排除的路径**

仓库里被 git 排除的文件不归 tcas 管。git 的三种排除来源都算（实测 `git check-ignore` 都认）：

| 来源 | 例子 |
|---|---|
| 仓库里的 `.gitignore`，包括子目录里的 | `dist/`、`node_modules/` |
| 这份检出本地的 `.git/info/exclude` | 只在本机排除的草稿目录 |
| 用户全局的排除文件（`core.excludesFile`） | `.DS_Store`、编辑器的临时文件 |

- **还不存在的文件也认。** 要在被排除的目录里新建文件时，同样直接放行（实测）。
- **按路径所属的检出判断。** 链接的 worktree 和主检出用同一份 `.git/info/exclude`，各自的 `.gitignore` 是各自检出的内容（实测）。
- **已经被 git 跟踪的文件不算被排除**，哪怕它符合某条排除规则（实测：被强制加进仓库的 `dist/keep.js`，git 不认为它被排除，改了之后 `git status` 照样列出）。它是仓库内容的一部分，照常要租约。
- **被排除的目录里嵌着的检出不跟着豁免。** Claude Code 自己建的 worktree 在 `.claude/worktrees/` 下，`.claude/` 常常被排除；从主检出问，worktree 里的文件是「被排除的」，但那是另一个检出里被跟踪的文件（实测）。所以先找所属的检出、再在那个检出里问（第 6、7 步的顺序），worktree 里的文件照常要租约。
- **被排除的检出不被发现，但发现了就管。** 目录扫描不进入被排除的目录，所以放在里面的普通嵌套仓库（如拉下来的第三方源码）不会被当成仓库来对账；`git worktree list` 找到的 worktree 除外。
- **不能申请被排除路径的租约。** 申请时直接说明它不归 tcas 管，不记租约。目录租约覆盖的范围里有被排除的子目录时，那部分照样不管。
- **中途变成被排除的**（往 `.gitignore` 或 `.git/info/exclude` 里加了规则）：之后对它的编辑直接放行；上面已有的租约在下一次有人申请、或查看状态时发现并释放。
- **怎么查**：`git check-ignore`，在路径所属的检出里运行。结果按路径缓存，这个检出的任何一个 `.gitignore`、`.git/info/exclude` 或全局排除文件变了就清空。实测一次约 9 毫秒，也可以一次问很多条路径（400 条约 16 毫秒）。

代价：两个会话同时改同一个被排除的文件（如 `.env.local`）时没有任何保护。它们本来就不进仓库，对账也看不到。要管其中某个文件，把它从排除规则里拿出来，或者用 `git add -f` 让 git 跟踪它。

**三种「不管」的区别**

| | 是什么 | 在哪里配 | 范围 |
|---|---|---|---|
| 豁免的目录 | 整个目录不管，也不能被打开 | `config.toml` 或 `.tcas.toml` | 任何地方，按目录 |
| 被 git 排除的路径 | git 不跟踪也不会跟踪的文件 | 仓库的 `.gitignore`、`.git/info/exclude`、全局排除文件 | 一个检出 |
| `unmanaged` | 仓库里被跟踪、但不想发租约的文件，如 lockfile | `.tcas.toml` | 一个根或一个仓库，按文件名模式 |

`tcas lease who <路径>` 会说明一条路径是不是不归 tcas 管，以及是哪一种、哪一条规则。

### 多个仓库

一个根目录可以装着几个仓库，例如 `~/Code/app/` 下有 `web/` 和 `api/` 两个检出，会话从 `~/Code/app/` 启动，同时改两边。根目录本身不必是仓库。

租约的规则不变。路径相对所在的根，自然带着仓库所在的目录，所以相交、申请、期限、等待在几个仓库之间不需要任何特殊处理，一次申请可以同时包含几个仓库里的路径。要分仓库做的只有 git 的部分：

| 事情 | 做法 |
|---|---|
| 路径是否干净、是否被 git 排除 | 在路径所属的仓库里查 |
| Bash 调用前后的快照 | 每个仓库各拍一次（[harness.md](harness.md) 第 5 节） |
| 分支、`HEAD` | 每个仓库各记各的 |
| 命令护栏、git 钩子 | 按命令作用到的那个仓库判断；git 钩子装在每个仓库里 |
| 提交 | `tcas commit` 每个仓库提交一次（[daemon-and-cli.md](daemon-and-cli.md) 第 5 节） |
| 目录租约的大小限制 | 目录下各仓库被跟踪的文件数加起来算 |

**仓库是自动发现的**，不需要逐个登记：

- 打开 workspace 时扫描一次，之后每次打开 Bash 对账窗口时再看一遍，新克隆的仓库在下一次 Bash 调用时就被纳入。
- 扫描从每个根往下，碰到含有 `.git`（目录或文件）的目录就记下，并继续往里找嵌套的检出。不进入被 git 排除的目录，深度有上限（[daemon-and-cli.md](daemon-and-cli.md) 第 6 节）。
- 另外对每个发现的仓库运行 `git worktree list`，把落在 workspace 里的链接 worktree 都记下。扫描会漏掉在被排除的目录里或太深的 worktree，这一步不会（实测）。
- 编辑工具的路径不靠扫描结果，上面的第 6 步是现查的。

**嵌套的检出各算一个仓库**（实测）：

| 情况 | git 的行为 | 处理 |
|---|---|---|
| 一个仓库的目录里放着另一个仓库（不是子模块） | 外层仓库只看到一个未跟踪的目录，看不到里面的改动 | 里面的文件归内层仓库。外层的快照里跳过这个目录 |
| 子模块 | 子模块里有改动或提交时，外层把子模块的路径本身报为有改动 | 子模块里的文件归子模块。子模块的路径本身（外层记录的提交号）是外层仓库的一条路径，可以单独取得租约 |
| 链接的 worktree（`git worktree add`） | 有自己的工作目录、分支和暂存区，和主检出互不影响 | 算一个独立的检出，见下面的「worktree」 |

**不属于任何仓库的文件**（多仓库的 workspace 里，直接放在根目录或仓库之间的文件）：改它照样取得租约，互斥照样成立。但它没有「干净」一说，所以按显式租约处理：持有者主动释放、超过期限没用到，或会话结束时释放，不会变成遗留租约。`tcas commit` 不管它。

**同一个仓库在两个 workspace 里各有一份检出**时，两边的租约互不相干。它们是磁盘上的两份文件，冲突在合并时由 git 处理。

**被 git 排除的路径不管**，规则见上面的「豁免」。配置里列为不管理的路径（`unmanaged`，如 lockfile）同样不发租约、不拦截，见 [daemon-and-cli.md](daemon-and-cli.md) 第 6 节。

### worktree

链接的 worktree（`git worktree add`）是同一个仓库的另一份检出：有自己的目录、分支和暂存区。tcas 把每个 worktree 当成一个独立的检出。几个会话在同一个 worktree 里工作，和在普通检出里一样：改文件取得租约、被拒、等待、`tcas commit` 都不变。

**按「仓库」说的规则，对 worktree 都是按检出算的。** 命令护栏和 git 钩子里的「这个仓库里有别的会话持有租约」，指的是这个 worktree 里。主检出里有人在工作，不妨碍另一个 worktree 里变基或 stash；反过来也一样。

| 事情 | 在 worktree 里 |
|---|---|
| 租约的路径 | worktree 的目录本身就在路径里。主检出的 `src/a.ts` 和 worktree 的 `src/a.ts` 是磁盘上的两个文件、两条路径，互不相干 |
| 干净与否、Bash 快照、分支 | 在这个 worktree 里查（实测：在 worktree 里改文件、变基，主检出的状态都不变） |
| `tcas commit` | 提交到这个 worktree 当前的分支 |
| git 钩子 | 配置是整个仓库共用的，装一次，主检出和所有 worktree 都生效（[harness.md](harness.md) 第 5.6 节） |
| stash | 列表是整个仓库共用的（实测：在 worktree 里存的，主检出里看得到、取得出）。`git stash` 只还原发起它的那个检出，所以按那个检出判断 |

**worktree 要在 workspace 里才受管理**

| worktree 在哪里 | 怎么办 |
|---|---|
| 在 workspace 的目录里。Claude Code 自己建的都是这样（实测）：`claude --worktree <名字>` 建在 `<仓库>/.claude/worktrees/<名字>`，子 agent 用 worktree 隔离时建在 `<仓库>/.claude/worktrees/agent-<编号>` | 自动发现，不用做任何事 |
| 在 workspace 外面，如 `git worktree add ../app-feature` | 把它加进同一个 workspace：`tcas workspace add ../app-feature`。打开主检出时会列出仓库在外面的 worktree 和对应的命令，但不替你加。这条命令用户和会话都可以运行，会话自己建的 worktree 可以自己加 |

没加进来的 worktree 里，会话不受约束，也不受保护。

**worktree 被删掉时**（`git worktree remove`，或者 harness 自己清理）：它下面的租约全部释放，文件已经不存在了。tcasd 在下一次发现仓库时注意到目录不在。

**子 agent 的隔离 worktree**：子 agent 算在父会话名下（第 9 节）。它在自己的 worktree 里改的文件，租约记在父会话名下，路径在那个 worktree 里，不会和主检出里的会话相撞。

## 4. 目录租约和相交

租约可以落在一个文件上，也可以落在一个目录上。目录租约覆盖目录下的所有路径，包括子目录和还不存在的文件：别的会话不能改、不能新建这个目录下的任何东西，也申请不到其中的任何路径。

| 两条路径 | 相交的条件 |
|---|---|
| 文件和文件 | 相同 |
| 目录和文件 | 文件在目录之下 |
| 目录和目录 | 一个包含另一个 |

**目录租约只表示范围，实际改了哪些文件另外记。** 会话在自己的目录租约下改一个文件时，tcasd 照样给这个文件记一条隐式的文件租约。这样：

- 目录租约放掉之后（让出、主动释放、会话结束），改过没提交的文件仍然各有一条文件租约保护着，目录里其余的部分别人可以用。
- `tcas commit` 知道该提交哪些文件：这个会话改过的，不是目录下所有有改动的。
- 统计得出事先申请的范围和实际改动的差（[daemon-and-cli.md](daemon-and-cli.md) 第 5 节）。

**规则上的差别**

- 目录租约只能事先取得（`tcas lease acquire`、`tcas lease wait`、用户的 `tcas lease grant`），不会自动产生。不论来源，都按显式租约处理（第 6 节）。
- 目录租约没有「干净」一说。它下面改过的文件由各自的文件租约负责。
- 目录还不存在也可以申请，用来占住一个将要新建的目录。

**范围的限制**

- 不能申请某个根目录本身，那等于锁住一整片。根里装着几个仓库时，可以申请其中某个仓库的根目录（如 `api/`），只要它不超过下面的限制。
- 目录下被跟踪的文件超过 200 个时拒绝（`max_dir_files`），提示改为申请更小的目录或列出具体文件。用户用 `tcas lease grant` 发的不受这个限制。

目录租约放掉之后，目录下没有记到这个会话名下的改动（用户改的，或 tcasd 看不见的写入）没有租约保护，和别处未归属的改动一样列在 `tcas status` 里。

## 5. 申请

会话 S 申请路径 p，按顺序判定：

1. p 不归 tcasd 管（第 3 节）：放行，不记租约。
2. S 自己已有覆盖 p 的租约：通过，并更新那条租约的使用时间（第 6 节）。两种情况另外记一笔：
   - 申请来自 `tcas lease acquire`，p 上是 S 的隐式租约：升级为显式（`cli`）。
   - 申请来自编辑工具或 Bash 对账，p 是一个文件，只被 S 的目录租约覆盖：给 p 记一条隐式的文件租约（第 4 节）。
3. 找出和 p 相交、且不属于 S 的租约 C。
4. C 里**可以让出**的租约，当场检查路径是否干净，干净的立即释放（目录租约不看干净与否，见第 4 节）。可以让出的有四种：
   - 遗留租约（`orphaned`）。
   - 活着的会话的隐式租约。
   - 活着的会话的显式租约和等来的租约，且已经过了期限（第 6 节）。
   - 活着的会话的显式租约，持有者提交过它，而且这一轮已经结束（第 6 节「提交过的显式租约」）。

   后三种还要求持有者此刻没有正在进行的、指向这个路径的编辑调用，也没有开着的 Bash 窗口（[harness.md](harness.md) 第 5 节；后台命令的窗口只算头 60 秒，见第 5.3 节）。
5. C 空了：授予。否则拒绝，返回剩下的持有者。

没过期限的显式租约和等来的租约不让出。有未提交改动的文件，它的文件租约不论哪一种、过了多久，都不让出。

一次申请多条路径是**全有或全无**：有一条被拒，一条也不授予。整个判定在一个事务里完成，路径分属几个仓库时也一样。申请一个目录时，目录下只要还有一条别人的租约没空出来，整个申请就被拒，输出里逐条列出是哪些路径、谁持有。

申请本身不等待，失败立即返回，并告诉 S 可以用 `tcas lease wait` 等（第 7 节）。S 不等的话，tcasd 记下它对这条路径感兴趣，路径空出来时通知它一次（[harness.md](harness.md) 第 6 节）。

**干净**的定义：`git status --porcelain -- <路径>` 没有输出，即和 `HEAD`、暂存区都一致，也不是未跟踪的文件。只对文件租约有意义。

**授予一个已经有未提交改动的路径**（用户改过，或上一个持有者被强制释放）：照常授予，同时告诉 S 这个文件有不是它做的未提交改动。

### 两种模式

| 模式 | 编辑工具碰到没人持有的路径 | 适合 |
|---|---|---|
| `auto`（默认） | 自动授予（`source: edit`），放行 | 日常使用，agent 不需要改变做法 |
| `strict` | 拒绝，提示先运行 `tcas lease acquire` | 想让 agent 事先说清楚要改哪些文件时 |

两种模式下，别人持有的路径都被拒绝，`tcas lease acquire` 都可用。

### 先申请再动手

**做较大的改动时，建议先申请租约，拿到之后再开始改。** 这在 `auto` 模式下是建议，不强制；要强制就用 `strict`。

「较大的改动」指下面任何一种：

- 要改三个或更多文件。
- 改动集中在一个目录或模块里，或者要新建文件、新建目录。
- 重命名、移动、批量替换。
- 要用脚本或命令来改（`sed -i`、代码生成、格式化工具）。

申请的范围说不准时用目录，说得准时列出具体文件，两种可以混着写：

```
tcas lease acquire src/auth/ --brief "Rename getUser to fetchUser in src/auth and update all callers"
tcas lease acquire src/auth/ src/api/user.ts --brief "..."
```

为什么要先申请：

- **冲突在动手之前暴露。** 申请是全有或全无的，拿不到时还没有改任何东西，可以换个做法、等，或者告诉用户。自动取得要改到一半才发现有个文件被占着，这时已经留下了一批改到一半的文件。
- **Bash 的写入只有这样才能事先保护。** 编辑工具每次调用前都会检查租约，脚本和命令不会（[harness.md](harness.md) 第 5 节）。大的改动常用脚本做，先占住目录，别的会话就不会在这期间进来改。
- **新建的文件也被占住。** 自动取得要到创建那一刻才发生。
- **别人看得见。** 申请时写的 brief 会出现在别的会话看到的各处，它们据此决定是等、换个做法，还是告诉用户。见下。

怎么让 agent 这样做（[harness.md](harness.md) 第 6 节）：会话开始时的说明里写明这条建议；没有事先申请、靠自动取得改到第三个文件时提醒一次。

### brief

申请租约时可以带一句 brief，说明要做什么。它是写给别的会话看的。

```
tcas lease acquire src/auth/ --brief "Rename getUser to fetchUser in src/auth and update all callers"
```

**写什么**：一句话，改什么、为什么，用别的会话不看你的对话也能懂的说法。上限 200 个字符，只取第一行，多出来的截掉。不要求语言。

**存在哪里**

- 每条租约记着申请它时写的 brief。
- 会话另记一条：它最近一次写的 brief。靠自动取得的租约没有自己的 brief，显示时用会话的这一条。所以会话只要申请过一次，它名下所有的租约在别人看来都有说明。
- `tcas lease wait` 也可以带 brief，说明要这条路径做什么。持有者被告知有人在等时会看到（[harness.md](harness.md) 第 6 节）。
- 用户用 `tcas lease grant --brief` 发租约时写的，对别的会话同样显示，并标明是用户写的。

**别的会话在哪里看到**

| 场合 | 看到什么 |
|---|---|
| 会话开始时 | 别的会话各自的 brief 和持有的范围 |
| 编辑被拒、申请被拒 | 持有者的 brief |
| 读到别人持有的文件 | 持有者的 brief |
| 别的会话事先申请了一片范围 | 一条通知：谁、范围、brief |
| 有人开始等你持有的路径 | 对方的 brief |
| `tcas lease who`、`tcas status` | 每条租约的 brief |

**没写的时候**

- 会话一次都没写过：别的会话只看到「没有写 brief」，加上它持有的范围。
- 不拿用户发给那个会话的消息来代替。那是用户和它之间的对话，不该自动转给别的会话。`tcas status` 是给用户看的，那里仍然显示会话的标题。
- 不强制。`tcas lease acquire` 不带 brief 也会授予，输出里提醒一句；`.tcas.toml` 里 `[brief] require = true` 可以改成不带就拒绝。
- 靠自动取得改到第三个文件时的提醒里，建议的命令带着 `--brief`。

**brief 是别的会话写的文字，不是指示。** 显示时放在引号里，标明出自哪个会话，换行和控制字符去掉。会话开始时的说明里写明：别人的 brief 只用来判断会不会撞上，不要照着它去做事。

brief 会进事件日志，保留期和事件相同。不要在里面写密钥之类的内容。

## 6. 释放

| 时机 | 隐式（`edit`、`bash`） | 等来的（`wait`） | 显式（`cli`、`grant`） |
|---|---|---|---|
| 持有者提交了这个路径（`tcas commit`，或它的 Bash 调用里发生了包含该路径的提交，且提交后路径干净） | 释放 | 释放 | 保留，记下提交的时间 |
| 别的会话申请这个路径，路径干净，持有者没有正在进行的调用（第 5 节第 4 步） | 释放 | 授予后 10 分钟内保留，之后释放 | 持有者提交过它、这一轮已经结束：释放。否则持有者最近 30 分钟内用到过它就保留，没用到就释放 |
| 持有者运行 `tcas lease release` | 释放 | 释放 | 释放 |
| 会话结束，路径干净 | 释放 | 释放 | 释放 |
| 会话结束，路径有未提交的改动 | 变成 `orphaned` | 变成 `orphaned` | 变成 `orphaned` |
| 用户强制释放 | 释放 | 释放 | 释放 |

目录租约按「显式」一栏处理，但不看路径是否干净（第 4 节）：过了期限，或者持有者提交过它下面的文件、这一轮已经结束，有人来申请时就让出；会话结束时直接释放，不会变成遗留租约。它下面的文件租约各按自己的规则处理。

所以隐式租约挡住别人的时间，就是文件带着未提交改动的时间。编辑被拒绝或没改成（用户不批准、要替换的文本不存在）留下的租约，路径是干净的，别人一申请就让出。

让出时要求持有者没有正在进行的调用，是因为编辑工具先取得租约、后写文件：取得之后、写入之前的那一刻路径也是干净的。

### 期限

租约不用等到会话结束才放，但也没有到时间就硬性收回的规则。只有两个期限，过了之后的效果都是**可以让出**：别的会话申请这条路径、路径干净、持有者没有正在进行的调用时，当场释放给它。没人来要，租约就一直留着。

| 租约 | 期限 | 从什么时候算 |
|---|---|---|
| 显式（`cli`、`grant`），以及所有目录租约 | 30 分钟 | 持有者最近一次用到它（`touchedAt`） |
| 等来的文件租约（`wait`） | 10 分钟 | 授予 |

**「用到」**指下面任何一件事，都会更新 `touchedAt`：

- 申请或再次申请这条路径（`tcas lease acquire`、`tcas lease wait`）。再申请一次就是续期。
- 用编辑工具改它，或用读文件、搜索工具读它。Bash 里的 `cat`、`grep` 看不到，不算。
- Bash 对账发现它变了。
- 提交了它。

目录租约下面任何一个文件被用到都算。

**为什么按用到的时间算**：agent 开工前先申请一批文件，然后花时间读代码，这段时间读的就是这些文件，租约一直是新的。申请了却半小时没碰，多半是不打算改了，或者会话已经没人管。

**有未提交改动的文件，它的租约没有期限。** 放掉它，别的会话就会在改到一半的文件上接着改。它挡住别人的时间，只取决于那些改动什么时候被提交、丢弃或转交。

- 持有者一旦改了文件，保护它的就是未提交的改动，和期限无关。
- 持有者提交之后，隐式租约和等来的租约当场释放；显式租约保留，期限从这次提交重新算，另外按下面「提交过的显式租约」处理。
- 目录租约到了期限照样可以让出。它下面改过没提交的文件各有自己的文件租约，留在原持有者名下；让出的只是目录里其余的部分。

只通过 Bash 读文件的会话，租约可能在它还在读的时候让出。后果是它收到通知，要用时再申请一次。

**让出时**给原持有者留一条通知（[harness.md](harness.md) 第 6 节）。它之后要改这个文件，要重新取得租约，文件可能已经被别人改过。目录租约让出时，通知里列出它名下还留着哪些文件。

### 提交过的显式租约

agent 事先申请了一个文件或目录，改完、提交了，却忘了释放。没有这一条的话，等着它的会话要再等 30 分钟（[walkthrough.md](walkthrough.md) 第 6 节）。

| 持有者 | 别的会话来申请或在等时 |
|---|---|
| 这一轮还在进行（`active`），或者有正在进行的调用 | 保留。它可能还要接着改 |
| 这一轮已经结束（`idle`：`Stop` 触发过，之后没有新的调用） | 让出 |

- **条件**：显式租约（`cli`、`grant`），持有者在取得它之后提交过它（文件租约：这个文件；目录租约：它下面的任何文件），并且文件租约的路径现在是干净的。有未提交改动的文件照旧不让，目录租约让出时它下面没提交的文件仍各有自己的文件租约。
- **没人来要就不放**。持有者下一轮回来，租约还在。
- **持有者在下一轮开始之前被告知**：让出的通知在它下一轮的第一个 hook（`UserPromptSubmit`，续接时是 `SessionStart`）里注入，排在最前，模型做任何事之前就看到哪些路径给了谁、要接着改就重新申请并重读（[harness.md](harness.md) 第 6 节）。
- **在等它的会话当场拿到**：持有者的 `Stop` 会让 tcasd 重新判定在等这些路径的等待（第 7 节）。
- 代价：会话停下来问用户一个问题，这期间别人来要，它提交过的范围就让出去了。它回来时被告知，重新申请即可；文件是提交过的，不会丢东西。
- 30 分钟的期限照旧，两条哪条先满足都算。

### 停滞的租约

路径有未提交改动，且持有会话超过 30 分钟没有任何活动（`lastSeenAt`）的租约，标为**停滞**。它是算出来的，不是一个状态，也不改变任何判定：这条租约照样挡住别人。

两种情况不算停滞，因为会话没有被丢下：

- 它有正在进行的调用，例如一条跑了很久的命令。调用期间没有 hook 触发，所以不能只看最后活动时间。
- 它正在等别的租约（第 7 节）。这时拒绝理由和 `tcas status` 里显示它在等哪条路径。

标出来是为了让人来处理：

- 拒绝理由里说明持有者已经多久没有活动，这条路径要等用户处理才会空出来，所以应该先告诉用户（[harness.md](harness.md) 第 4 节）。
- `tcas status` 里单独标出，并给出处理的命令。

用户可以回到那个会话让它提交，用 `tcas lease transfer` 转给另一个会话，或用 `tcas lease release --force` 强制释放。持有会话再有活动，标记自动消失。

停滞的租约和遗留租约的区别只是持有会话还在不在，处理方式相同。

这三个时长都是配置项（[daemon-and-cli.md](daemon-and-cli.md) 第 6 节）。

### 会话结束

触发：harness 的 `SessionEnd` hook；或者 tcasd 发现会话的进程已经不在（每 15 秒检查一次，PID 和进程启动时间都对得上才算活着）。

处理：

1. 关掉它所有还开着的工具调用窗口（[harness.md](harness.md) 第 5 节）。
2. 目录租约直接释放。
3. 查它每条文件租约的路径是否干净，每个涉及的仓库一次 `git status`。干净的释放，不干净的变成 `orphaned`。不属于任何仓库的文件直接释放。
4. 会话标为 `ended`。

### 遗留租约（`orphaned`）

持有会话已经结束、文件还有未提交改动的租约。它仍然挡住别的会话，因为那是改到一半的文件。拒绝理由里会写明这是遗留租约、原会话是谁、用户可以怎么处理。

清除的方式：

| 方式 | 结果 |
|---|---|
| 原会话续接，或它的任何一个 hook 再次联系 tcasd | 会话回到 `active`，它的遗留租约回到 `active` |
| 用户提交或丢弃了那些改动 | 路径变干净。提交的当场释放（git 的 `post-commit` 钩子，[harness.md](harness.md) 第 5.6 节）；丢弃的在下一次有人申请时释放，有会话在等它时几秒内被发现 |
| 用户运行 `tcas lease transfer --to <会话>` | 转给另一个会话，由它接着改 |
| 用户运行 `tcas lease release --force` | 释放。接手的会话会被告知文件里有别人留下的未提交改动 |

丢弃改动没有钩子可挂，所以是惰性的：tcasd 平时不轮询工作目录，只在有人申请或查看状态时现查。有会话在等这条路径时每 5 秒查一次（第 7 节）。

harness 进程不变、会话 ID 换了的情况（如 `/clear`），新会话接过旧会话的租约，不产生遗留租约，见 [harness.md](harness.md) 第 2 节。

无界面模式下每次 `claude -p` 是一个进程，进程退出就是会话结束，`--resume` 时会话 ID 不变（实测），所以两轮之间的脏文件由遗留租约保护，续接后自动接回。目录租约和干净的显式租约在每一轮结束时释放，下一轮要用就重新申请。

## 7. 等待

被拒之后，会话可以用 `tcas lease wait <路径…>` 等。它的判定和 `tcas lease acquire` 相同（全有或全无），区别是拿不到时不返回，一直等到能全部授予、超时，或者被判定为死锁。拒绝理由里会给出这条命令（[harness.md](harness.md) 第 4 节）。

**等待不占会话的主线程。** 这条命令用 harness 的异步机制运行（Claude Code 是后台 shell）。agent 在等待期间继续做别的，或者结束这一轮；结果出来时由 harness 和 hook 送回会话。在前台运行会被 hook 改成后台。做法见 [harness.md](harness.md) 第 6 节。

**何时授予**

tcasd 在这些时候重新判定每个等待：

- 租约表有变化：释放、让出、转交、会话结束。
- 被等待路径的持有者有一次调用结束。它的隐式租约这时可能可以让出了。
- 被等待路径的持有者这一轮结束（`Stop`）。它提交过的显式租约这时可以让出了（第 6 节）。
- 被等待的租约过了期限（第 6 节）。tcasd 按到期的时刻重新判定，不靠轮询。
- 仓库里发生了提交（git 的 `post-commit` 钩子）。
- 还有等待存在时，每 5 秒查一次被等待的路径是否干净。用户丢弃了遗留租约的改动，或者仓库没装 git 钩子时，靠这一条发现。

一个等待的全部路径都能授予时，立即授予（`source: wait`），命令返回。释放和授予在同一个事务里，路径不会在中间被第三个会话拿走。授予之前确认等待方的会话进程还在。

**等到之后**

等待是异步的，从授予到会话真正开始改文件之间有一段时间：它要先被唤醒，或者做完手上的调用。这段时间里路径是干净的，所以等来的租约授予后保留 10 分钟，期间不让给别人。之后按第 6 节的期限处理，等到了却没有回来用的会话（没被唤醒，或者改了主意）不会一直占着路径。

**多个会话等同一条路径**

- 谁的路径先凑齐谁先拿；同时凑齐的，先开始等的先拿。
- 等待不是预约。一个等待的路径没凑齐时，其中已经空出来的路径别人可以拿走。
- 代价：要等多条路径的会话可能一直凑不齐，靠超时结束。

**等一个目录**

可以等目录。要等到目录下别人的租约全部空出来才授予，目录越大越难凑齐。等到的目录租约按显式租约处理（第 4 节）。

**死锁**

持有租约的同时可以等待，所以两个会话可能互相等。tcasd 维护一张等待图（等待的会话指向它所等路径的持有者），每次登记等待和每次租约表变化后检查：

- 登记时就会成环：拒绝登记，命令立即返回，说明环是怎么形成的（你持有的哪条路径正被谁等，它又持有你要的哪条）。
- 之后才成环（被等待的路径换了持有者）：结束环里最晚开始的那个等待，同样说明原因。

被结束的一方该做的是先提交或释放别人在等的路径，或者告诉用户。

死锁检查只看得见用 `tcas lease wait` 等的会话。一个会话被拒后停下来问用户，另一个在等它持有的路径，这种情况靠超时结束。

**超时**

`--timeout <秒>`，默认 1800（30 分钟）。到时间没拿到就返回，说明每条路径现在被谁持有。超时的命令不留下任何状态，再运行一次就是重新开始等。

等待在后台进行，超时的作用是给 agent 一个重新决定的时机：死锁检查看不见的互相等待、没人处理的遗留租约，都靠它结束。

**取消**

等待绑定在 `tcas lease wait` 进程和 tcasd 的连接上，连接断开就取消。会话结束时 tcasd 也取消它的全部等待。tcasd 重启时命令自动重连并重新登记，保留原来的开始时间。

**等遗留租约和停滞的租约**

可以等，但它要到用户处理之后才会空出来（第 6 节）。拒绝理由和超时信息里都会说明这一点，这种情况应该先告诉用户。

## 8. 不变量

实现和测试都以这几条为准：

1. 任意时刻，同一个 workspace 里任何两条租约要么不相交，要么属于同一个会话。
2. 申请要么全部授予，要么一条也不授予。
3. tcasd 不写、不还原、不删除 workspace 里的任何文件，也不改索引和 `HEAD`。只有两处例外：各仓库 git 配置里 tcas 自己的那一行引用，由 tcasd 在打开、关闭 workspace 和发现新仓库时用 `git config` 加上或去掉（git 自己加锁）；`tcas commit` 由命令行进程执行，只提交本会话租约之下的文件。
4. 租约表的每次变化都有一条事件，变化和事件在同一个事务里。
5. 拦截路径上（编辑工具和 Bash 的 `PreToolUse`）tcasd 不可用时拒绝，不放行。
6. 一个会话的任何 hook 联系 tcasd，都会让它回到 `active`。误判会话已结束的后果只是短暂的状态不准。
7. 等待图里没有环。每个等待都会结束：授予、超时、取消，或被判定为死锁。
8. 有未提交改动的文件，它的文件租约只会因为持有者自己的操作（提交、主动释放）或用户的操作（丢弃改动、转交、强制释放）而释放。时间和别的会话的申请都不会让它释放。
9. 会话经由编辑工具改过、或经由 Bash 对账记到它名下、还没提交的文件，都有一条它名下的文件租约，不论它是否还持有覆盖这个文件的目录租约。

## 9. 没有覆盖的情况

- **同一个会话的两个子 agent 互相不隔离**。hook 输入里有 `agent_id`，但 Bash 环境里只有父会话的 ID（实测），命令行分不清是哪个子 agent。事件日志里记了 `agent_id`，需要时可以把持有者细化到子 agent。
- **不经过编辑工具和 Bash 的写入**（如 MCP 工具写文件、放到后台继续跑的命令）拦不住，也没有对账窗口。`tcas status` 会列出「有改动但没人持有」的路径。
- **跨仓库的提交不是原子的**。一次改动涉及几个仓库时，`tcas commit` 逐个仓库提交，中间失败会留下一部分已提交、一部分没提交。它会说明哪些成功了，没提交的文件租约不变。
- **被 git 排除的文件没有保护**（第 3 节）。两个会话同时改同一个 `.env.local` 不会被发现。
- **workspace 外面的目录**。会话改到外面的检出时只有提示（第 3 节），没有租约；Bash 对外面的写入看不到。
- **用户的改动不受约束**。用户改了某个会话持有的文件，tcasd 不知道，除非它落在某次 Bash 调用的窗口里。用户的 git 操作里，提交、变基和 stash 会被 git 钩子检查（[harness.md](harness.md) 第 5.6 节），其余的不会。
- **等待没有预约**（第 7 节）。先开始等的会话不保证先拿到。
- **先申请只是建议**（第 5 节）。`auto` 模式下 agent 可以不申请就开始改，这时大的改动仍然可能改到一半才撞上别人。
