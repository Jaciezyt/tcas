# TCAS 设计文档

以任务调度为核心的多 Agent 系统。名字取自飞机的空中防撞系统：让多个 agent 在同一个项目里并行工作而不相撞。

状态：设计草案，2026-11-19 立项
主页：tcas.io
范围：整体架构、任务与租约模型、隔离与验证、多机器、记忆、harness 集成、实施顺序

**部件命名**

| 名称 | 是什么 |
|---|---|
| `tcas` | 命令行，用户和 agent 都用它操作任务板 |
| `tcasd` | 每台机器上的 daemon |
| `tcas-hook` | 三家 harness 共用的 hook 程序（10.5） |
| `tcas-mcp` | 提供给 agent 的 MCP 服务（10.5） |
| 控制面 | 任务库、事件日志、租约表、调度器、记忆库、变更集库 |

---

## 1. 目标与原则

**目标**：让多个 coding agent 在同一个项目上并行工作，把花在冲突处理和重复劳动上的时间降到最低，并且用户可以随时远程查看和调整。

**原则**

1. **调度优先于角色**。agent 是同质的 worker，差异只来自三样配置：拿到的上下文、可用的权限、要求的输出。不设人设。
2. **冲突在批准时解决，不在合并时解决**。任务开工前声明影响面，调度器据此决定并行还是排序。
3. **隔离和验证都分级**，每次选够用的最便宜一级。worktree 和集成验证都可以用，但都是按需手段。
4. **状态在任务板上，不在任何 agent 的上下文里**。任何会话都可以被压缩、重启或替换。
5. **使用现成的 harness**（Claude Code、Codex 等）作为 worker 运行时，本系统只做控制面和每台机器上的 daemon。
6. **确定性的事情不交给 LLM**。重叠判定、排序、租约、验证触发都是规则；LLM 只负责方案、实现、审查和分诊。
7. **控制面和 daemon 不依赖任何 AI provider**。所有 agent（包括 leader）同时掉线时，系统状态仍然完整、可查看、可恢复。见第 13 节。

## 2. 架构

```
        用户（UI / CLI，可远程）
                 │
        ┌────────▼────────┐
        │     控制面       │  任务库 · 事件日志 · 租约表 · 调度器 · 记忆库
        └────────▲────────┘
                 │  daemon 主动连出
     ┌───────────┼───────────┐
┌────┴─────┐ ┌───┴──────┐ ┌──┴───────┐
│ daemon A │ │ daemon B │ │ daemon C │   每台机器一个
└────┬─────┘ └────┬─────┘ └────┬─────┘
  workspace     workspace    workspace     每个 workspace：共享工作目录 + 沙箱池
  └ harness 会话（PM / team lead / worker / reviewer / tester）
```

| 组件 | 职责 |
|---|---|
| 控制面 | 单一实例。保存任务、事件、租约、记忆和变更集；运行调度规则；对外提供 API |
| daemon | 启动和停止 harness 会话；执行租约拦截和事后对账；收集变更集、管理沙箱；上报事件 |
| harness 会话 | 实际干活的 agent，通过 hooks 和 MCP/CLI 接入系统 |
| UI / CLI | 只和控制面通信，用户和 leader 对话、查看任务板、手动干预 |

**Project 和 workspace**

| 层 | 是什么 | 拥有什么 |
|---|---|---|
| Project | 一项工作的整体，包含一个或多个 git 仓库 | PM、team lead、模块、任务、记忆、配置 |
| Workspace | 某台机器上这个 project 的一组检出（每个仓库一份，可以只含部分仓库） | 工作目录、沙箱池、会话；本机租约的拦截和对账 |

单机、单仓库的用户感觉不到这两层：project 默认只有一个仓库和一个自动创建的 workspace。细节见第 8 节。

## 3. 角色

角色是权限和上下文的配置，不是人设。

| 角色 | 权限 | 上下文 | 生命周期 |
|---|---|---|---|
| PM | 只读代码；可创建、修改、批准、排序任何任务；可改项目级配置 | 全局目标、任务板 | 长期，每个 project 唯一 |
| Team lead | 只读代码；对所负责的域内任务有同样的权限；可改域内配置 | 所负责的域：模块、任务、记忆、统计 | 长期，按需设置 |
| Worker | 租约内可写 | 单个任务的 brief、相关记忆 | 一个或几个任务 |
| Reviewer | 只读 | diff、方案、影响面、相关不变量；不看执行者的推理 | 一次审查 |
| Tester | 只能在沙箱里写 | 待验证的变更集或批 | 一次验证 |

机械的检查（类型检查、测试、构建）由 daemon 按检查映射执行（7.3），不经过模型。tester 只处理需要判断的部分：验收标准里没有对应检查的条目（复现一个行为、走一遍手工步骤）、验证失败的归因、二分结果的解读。

### 3.1 组织结构：扁平

```
用户
 └ PM（每个 project 唯一）
     ├ team lead：域 A（一组模块）      ← 按需设置，可以一个都没有
     ├ team lead：域 B
     └ ……
worker / reviewer / tester：全局池，按任务派发，不属于任何 lead
```

- **不设 team 这个实体**。worker 是临时会话，没有固定归属。「team」只是「一个 team lead 加它负责的模块」的视图，是推导出来的。
- **最多两层**：PM 和 team lead。team lead 之下不再设 lead，每多一层就多一次转述和信息损失。
- **执行资源是全局池**。可以按域设并发上限，防止一个域占满所有 worker，但空闲的额度别的域可以借用。

本文其余部分的「leader」是 PM 和 team lead 的统称。任务的 **owner leader** 指：任务所在模块有 team lead 时是该 team lead，否则是 PM。

### 3.2 PM

- 每个 project 有且只有一个，是项目的最高负责人，不管 project 有几个仓库、几个 workspace。用户主要和它对话。
- 负责：目标和优先级、任务组、跨域任务的拆分和归属、team lead 之间的仲裁、项目级配置。
- 没有 team lead 的模块由 PM 直接负责。小项目可以只有 PM。
- 可以推翻任何 team lead 的决定，推翻时记录理由。

### 3.3 Team lead

- 按需设置，各负责一个域（一组模块），域之间不重叠。域可以跨仓库，例如「支付」同时包含后端和前端仓库里的模块。
- 负责域内的方案审批、新任务和待分诊项的分诊、代答用户输入、确认无效任务、批准记忆。
- 对域外的任务只能评论或提请求。
- **何时增设**由可观测的信号决定：PM 待决队列的等待时间、PM 名下的活跃任务数、某组模块的任务量和记忆量。系统在超过阈值时提示，由用户或 PM 决定。
- **何时撤销**：域长期没有活动时，模块交还 PM。域的状态都在任务板和记忆里，撤销和重设都不丢信息。

### 3.4 跨域任务

- 优先拆成每个域一个任务，用显式依赖连起来。
- 拆不开的归 PM 所有，相关的 team lead 评论。
- 域之间的边界争议（某个文件或接口归谁）由 PM 仲裁，结果落到模块定义上。

### 3.5 Team lead 对域的优化

team lead 不只是审批人，还要对所负责的域持续做优化。它只读代码，所以优化的对象是域的记忆和配置。

| 对象 | 做什么 |
|---|---|
| 记忆 | 批准或驳回候选记忆；处理 `stale` 的记忆；合并重复的、淘汰过时的；把反复被重新发现的事实补成记忆 |
| 域简报 | 维护一份简短的域说明：结构、约定、常见陷阱、验证方法。新会话在域内做方案时首先收到它，替代逐条投递的一部分 |
| 检查映射 | 调整域内路径对应的检查（7.3）：去掉多余的，补上漏验的 |
| 模块边界和依赖 | 发现模块划分不合理或依赖图缺边时，提议修改 |
| 热点文件 | 根据租约争用提议增减 |
| 默认值 | 域内的隔离级别、自动批准阈值、前提核实清单 |
| 任务质量 | 无效任务和影响面估错在域内反复出现时，调整拆任务的方式或补充前提清单 |

规则：

- **由信号触发，不靠自觉**。系统按域统计：`stale` 和候选记忆的积压、影响面估错率、验证漏检、无效任务率、租约争用、搁置后的返工率。超过阈值时给 team lead 生成一个维护任务。
- **维护工作本身是任务**，有目标、验收标准和结果，和其他任务一样留痕。例如「把域 A 的 `stale` 记忆清到 0，每条给出处理结论」。
- **权限按范围划分**：只影响本域的配置由 team lead 直接改；影响其他域或项目级的（模块边界、全局热点文件）只能提议，由 PM 批准。
- **改动可回溯**：配置变更是事件，记录改前改后和理由。改完后同一组信号用来检验是否真的变好，变差则提示回退。
- 没有 team lead 的模块，这些工作由 PM 承担。这也是增设 team lead 的一个信号。

### 3.6 共同规则

- 每个任务有唯一的 owner leader，避免在任务层面互相覆盖。
- 和用户对话中产生的决定必须落成任务或任务备注。leader 应能随时仅凭任务板重建现场。

### 3.7 身份和授权

上面的权限要生效，控制面必须知道每个请求是谁发的。worker 有 Bash，和用户的 CLI、daemon 的本机套接字在同一台机器上，所以身份不能靠调用方自己声明。

- **会话令牌**：daemon 启动会话时签发一个令牌，绑定角色、任务和 workspace，只交给这个会话的 `tcas-hook` 和 `tcas-mcp`。控制面和 daemon 按令牌鉴权，会话结束后令牌失效。
- **agent 用 `tcas` 命令行时带的也是会话令牌**，能做的事和通过 `tcas-mcp` 一样。
- **按令牌的角色鉴权**。批准方案、确认无效、代答、改配置只接受 leader 会话的令牌或用户凭据；worker 的令牌只能操作自己的任务。
- **用户凭据和会话令牌分开存放**，agent 的 Bash 读不到用户凭据。
- **本机套接字不接受匿名请求**，`tcas-hook` 的每次查询都带会话令牌。
- **威胁模型**：把 agent 当作会出错、会被读到的内容带偏的程序，不当作蓄意的攻击者。要保证的是它不能靠顺手跑一条命令越权。同一个系统用户下蓄意绕过的防护强度是未决问题（第 12 节）。

## 4. 任务模型

### 4.1 组织维度

- **模块（Module）**：隔离的基本单位，属于一个仓库，由该仓库内一组互不重叠的目录前缀定义，可以指定 team lead，不指定则归 PM。每个仓库另有一个隐含的默认模块，收纳没被任何前缀覆盖的路径（如仓库根的配置文件），归 PM。模块划分是整个系统里最值得用户投入的配置。
- **组（Group）**：用户定义的集合，如一个需求、epic 或里程碑。
- **优先级**：P0 到 P3。

任务库的作用域是项目，存放在控制面，通过 CLI 或 MCP 暴露给所有 agent。任何 agent 都可以阅读、新建、认领。不放在仓库文件里，原因是认领需要原子性、跨机器需要一致、状态变更不应污染提交历史。需要时可以向仓库导出只读投影。

### 4.2 数据结构

```ts
type Priority = 'P0' | 'P1' | 'P2' | 'P3'

interface Project {
  id: string
  name: string
  pm: AgentId                 // 唯一
  repos: Repo[]               // 一个或多个
}

interface Repo {
  id: string                  // 短名，用作路径前缀，如 "web"、"api"
  remote: string
  defaultBranch: string
}

interface Workspace {
  id: string
  project: ProjectId
  machine: MachineId
  checkouts: Record<RepoId, string>   // 仓库 → 本机目录，可以只含部分仓库
}

type Snapshot = Record<RepoId, string>  // 每个仓库各一个 commit，合起来是 project 的一个基线

interface Module {
  id: string
  repo: RepoId                // 一个模块只属于一个仓库
  paths: string[]             // 目录前缀，模块之间不允许重叠
  teamLead?: AgentId          // 不设则由 PM 直接负责
}

interface Group {
  id: string
  name: string
  ownerLeader: AgentId        // 跨域的组归 PM
}

interface Task {
  id: string
  project: ProjectId
  workspace?: WorkspaceId     // 执行位置，派发时分配，不是任务的固定属性
  title: string
  goal: string                // 要达成什么，必填，见 4.6
  acceptance: Criterion[]     // 验收标准：怎样算达成，必填，每条可检验
  premises: string[]          // 任务成立所依赖的前提，planning 时逐条核实
  brief: string               // 背景和补充说明
  outcome?: Outcome           // 进入 done 前必填
  invalid?: {                 // 被判定为无效时填写
    reason: 'false_premise' | 'no_goal' | 'duplicate' | 'obsolete' | 'infeasible'
    detail: string
    evidence: string[]        // 文件、commit、会话或复现结果的引用
    foundAt: TaskState        // 在哪个阶段发现
    proposedBy: AgentId
    confirmedBy: AgentId | 'user'
    duplicateOf?: TaskId
  }
  group?: GroupId
  priority: Priority
  state: TaskState
  ownerLeader: AgentId
  assignee?: SessionId
  claimExpiresAt?: Time       // planning 阶段认领的过期时间
  plan?: string
  planBaseCommit?: Snapshot     // 方案基于的 commit，用于判断是否需要复核
  approvedAt?: Time           // 批准时间，排序用（5.2），搁置后恢复时保留
  footprint?: Footprint
  modules: ModuleId[]         // 由 footprint 推导，不手填
  batch?: BatchId
  isolation: 0 | '1A' | '1B' | 2        // 见第 6 节
  pausedReason?: 'lease_denied' | 'needs_input' | 'agent_lost' | 'provider_outage' | 'machine_unreachable' | 'user'
  pausedFrom?: TaskState      // 暂停前的状态，恢复时回到这里
  pendingInputs: InputRequestId[]   // 非空时任务被阻断，见 4.5
  shelf?: {                   // 暂停后已搁置：改过的文件已拷出保存，租约已释放，见 5.6
    changeSet: ChangeSetId
    baseCommit: Snapshot
    at: Time
  }
  rev: number                 // 乐观锁
}

interface Criterion {
  text: string
  check?: CheckId             // 检查映射里的某个检查（7.3），有它才能自动对照
}

interface InputRequest {      // 需要用户回答的问题
  id: string
  task: TaskId
  askedBy: AgentId
  question: string
  options?: string[]
  recommendation?: string     // 提问方建议的选项和理由
  delegable: boolean          // 超时后是否允许 leader 代答
  timeoutAt?: Time            // 不设则一直等用户
  status: 'pending' | 'answered' | 'delegated'
  answer?: string
  answeredBy?: 'user' | AgentId
  rationale?: string          // leader 代答时必填
}

interface Outcome {
  summary: string             // 实际达成了什么
  criteria: {                 // 与 acceptance 一一对应
    criterion: string
    met: boolean
    evidence: string          // commit、验证结果、产出文档的引用
  }[]
  artifacts: string[]         // commit、文档、报告等产出
}

interface Footprint {
  writes: string[]            // 已存在的具体文件
  creates: string[]           // 新文件的具体路径；名字定不下来时用目录前缀
  changes: InterfaceRef[]     // 要改的接口，如 "auth:SessionToken"
  dependsOn: InterfaceRef[]   // 依赖的接口
}

interface Edge {
  before: TaskId
  after: TaskId
  reason: 'write_overlap' | 'interface' | 'explicit'
  source: 'scheduler' | 'leader'
}

interface Lease {
  workspace: WorkspaceId      // 持有它的任务所在的 workspace；独占的范围是 project（5.3）
  path: string                // 带仓库前缀，如 "web:src/app.ts"
  task: TaskId
  kind: 'task' | 'short'
  batch?: BatchId             // 批内的路径由批持有，在成员之间按顺序交接（5.5）
}

interface Reservation {       // 排队中的任务对路径的预约，不占文件
  path: string
  task: TaskId
}

interface Batch {
  id: string
  tasks: TaskId[]             // 按执行顺序
  base: Snapshot
  branch: string              // 批分支，检查点提交在上面
  sealed: boolean
}

interface Session {
  id: string
  agent: AgentId
  role: 'pm' | 'team_lead' | 'worker' | 'reviewer' | 'tester'
  harness: string
  harnessSessionId?: string   // 续接用
  workspace: WorkspaceId
  task?: TaskId
}

interface TriageItem {        // 待分诊项，见 4.6
  id: string
  project: ProjectId
  body: string
  raisedBy: AgentId | 'user'
  fromTask?: TaskId
  ownerLeader: AgentId
  resolution?: { task: TaskId } | { discarded: string }   // 建成任务，或丢弃并写明理由
}

interface Handoff {           // 交接记录
  task: TaskId
  session: SessionId
  changedFiles: string[]
  remainingSteps: string[]
  notes: string               // 当前判断
  at: Time
}

interface Event {             // 所有状态变更的唯一来源
  seq: number                 // 控制面收到时分配，全局有序
  at: Time
  project: ProjectId
  task?: TaskId               // 配置变更、记忆状态变更等没有任务
  actor: AgentId | 'scheduler' | 'daemon' | 'user'
  origin?: { machine: MachineId, localSeq: number }   // daemon 离线缓冲的事件，用于保序和去重
  type: string
  payload: unknown
}
```

- 写集合用具体文件加目录前缀，不用 glob，这样求交集和判断包含都是确定的。
- **所有路径都带仓库前缀**（`仓库:路径`），包括影响面、租约、检查映射和记忆的锚点。这样重叠判定、租约、排序的规则在多仓库下不需要改。
- 一个任务的 `modules` 多于一个，是应该拆分的信号，提交方案时提示。
- 任务是事件溯源的。事件日志同时是审计记录和记忆的原料。
- `AgentId` 标识身份，`SessionId` 标识一次会话。leader 是长期身份，背后的会话可以更换；worker、reviewer、tester 的身份就是它的会话。
- 事件的 `seq` 由控制面在收到时分配。daemon 离线期间缓冲的事件带本地序号（`origin`），重连后按本地序号重放，控制面据此去重。

### 4.3 状态机

```
open → planning → proposed → approved → queued → in_progress → verifying → review → done
                                                      ↕
                                                    paused

verifying、review → in_progress（验证失败或审查不通过，租约不放）
任何未完成的状态 → invalid（任务本身不成立）
任何未完成的状态 → cancelled（任务成立，但决定不做）
```

| 状态 | 含义 |
|---|---|
| open | 任何 agent 可见、可认领 |
| planning | 已被原子认领（带过期时间），正在做方案和影响面。需要用户回答的问题在这一阶段提完；有未答问题时不能进入 `proposed` |
| proposed | 已提交方案和影响面，等待检查和批准 |
| approved | 检查通过 |
| queued | 前面有顺序边未完成；只持有预约，不占文件 |
| in_progress | 已获取租约，正在执行 |
| verifying | 变更集已收集，正在验证；租约继续持有。失败则回到 `in_progress`。批内任务打完检查点后也在这个状态等批验证，它的路径由批持有（5.5） |
| review | 验证通过，等待审查（小任务可跳过）；此时还没有提交，租约继续持有。不通过则带着审查意见回到 `in_progress` |
| paused | 暂停。原因记录在 `pausedReason`：扩租被拒、等待用户输入、agent 掉线、provider 故障、机器失联、用户操作。租约是继续持有还是搁置后释放，按 5.6 的偏好处理 |
| done | 审查通过后已提交，租约释放，`outcome` 已填写且验收标准全部满足 |
| invalid | 终态。任务的前提、目标或可行性有问题，不成立。见 4.6 |
| cancelled | 终态。任务成立，但用户或 leader 决定不做 |

### 4.4 认领与批准

**开工前必须先确定方案和影响面。影响面声明就是租约申请。**

1. agent 认领（或被分配）任务，进入 `planning`。
2. 提交方案和影响面。
3. 两层批准：
   - 调度器确定性检查路径和接口重叠，决定并行还是排序。
   - owner leader 判断方案本身；高风险任务可配置为需要用户确认。
4. **分级**：只写一两个文件、不改接口的任务，确定性检查通过即自动批准。阈值是项目级配置。

**主动认领的两种实际时机**

- 做完一个任务后接相邻任务。调度器按亲和度推荐：刚在同一模块工作过、上下文还在的会话优先。
- 执行中发现新工作。agent 提交给 leader 分诊，不顺手做掉，避免影响面悄悄膨胀。写得出目标和验收标准的直接建成任务，写不出的作为待分诊项提交（见 4.6）。

上下文已经很长的会话不再认领，结束并留下交接记录。

### 4.5 用户输入

**需要用户回答的问题在 `planning` 阶段提完，开工后不再问。**

理由是成本：`planning` 阶段的任务不持有租约，等多久都不挡别人；开工后再停下来等用户，会带着租约把后面排队的任务一起堵住。

**提问**

- agent 做方案时，把所有需要用户决定的事作为 `InputRequest` 提出：范围取舍、产品行为、不可逆的操作、方案之间的选择。
- 每个问题附选项和提问方的建议。这样用户答得快，超时后 leader 代答也有依据。
- 能从代码、记忆或已有任务备注里查到的事不问用户。
- leader 拆任务和分诊时向用户提问，用同一套机制。

**阻断**

- 任务有未答问题时不能进入 `proposed`，只阻断这一个任务，其他任务照常进行。显式依赖它的任务自然排在后面。
- 等待期间认领过期的计时暂停。会话可以先保存方案草稿并结束，回答到达后续接或交接，不必空占上下文。
- 所有未答问题汇总到用户的待答队列，按任务的 P 级和「挡住了多少后续任务」排序。

**超时后由 leader 决定**

- 默认不超时，一直等用户。用户可以设置超时时间，可以按项目、按 P 级或按单个问题设置。
- 到期后问题转给任务的 owner leader。leader 可以代答，并必须写明理由；也可以判断这件事不该由它决定，继续等用户。
- `delegable: false` 的问题永不超时。不可逆或对外的操作（删除数据、改公开接口、发布、花钱）默认属于这一类，类别由用户配置。
- leader 代答的问题标为 `delegated`，在任务上和 UI 里明确显示「由 leader 代为决定」。用户事后可以推翻，推翻时生成一个后续任务来修正，而不是回滚已落地的工作。
- 到期时 leader 不可用（见第 13 节），问题保持未答，继续等用户，不会无人决定就通过。

**开工后才出现的问题**

这说明方案不完整。是否暂停由用户的偏好决定，系统不替用户选：

| 偏好 | 行为 |
|---|---|
| `pause` | 任务进入 `paused`（`needs_input`），问题进入待答队列并适用同样的超时规则。租约按 5.6 处理；仍持有租约的任务，其问题在队列里排到同等 P 级的最前面 |
| `proceed` | agent 按方案的意图做出选择并继续，不暂停。问题和所做的选择记在任务上，进入用户的待答队列供事后确认，审查时也会列出 |
| `leader` | 问题直接交给任务的 owner leader 审核并选择，不等用户。leader 作答后 agent 继续；问题和 leader 的选择进入用户的待答队列供事后确认 |

- 偏好可以按项目、按 P 级或按单个任务设置，越具体的优先。
- `proceed` 和 `leader` 下用户事后不同意某个选择时，和推翻 leader 代答一样，生成一个后续任务来修正。

`leader` 偏好的细则：

- agent 提问时仍然附选项和建议。leader 可以采纳、改选，或给出不在选项里的答案，并必须写明理由。问题标为 `delegated`。
- leader 也可以判断这件事不该由它决定，**上交给用户**。此后按 `pause` 处理。
- 等 leader 答复期间任务是 `paused`（`needs_input`），通常很短。租约按 5.6 处理，短暂等待一般落在宽限时间内，不会触发搁置。
- leader 不可用时（见第 13 节）退回到 `pause`，问题进入用户的待答队列，不会无人决定就继续。
- 它和「超时后由 leader 决定」的区别是不先等用户：`pause` 加超时是用户优先、leader 兜底，`leader` 是 leader 优先、用户事后确认。
- 无论走哪种，系统都记录这次遗漏并挂到模块的记忆上，供以后在这个模块做方案时提示。

待确认：`delegable: false` 的问题（不可逆或对外的操作）是否无视 `proceed` 和 `leader` 一律暂停等用户。当前草案按一律暂停处理。

### 4.6 目标、结果与无效任务

**没有目标和结果的东西不是任务。**

**目标**

- 创建任务时必须填 `goal`（要达成什么）和 `acceptance`（怎样算达成）。缺任何一项，控制面拒绝创建。
- 验收标准每条都要可检验：某个检查通过、某个行为可以复现、某份产出存在。「优化一下」「看看这个模块」不满足要求。
- 能由检查判定的标准绑定到检查映射里的一个检查（`check`，见 7.3），其余的由 reviewer 或 tester 判断。
- 调研类工作也是任务，它的结果是一个结论或一份文档，验收标准写明要回答什么问题。
- `premises` 列出任务成立所依赖的前提，例如「这个 bug 在当前主线上可以复现」「接口 X 目前返回的是 Y」。

**待分诊项**

agent 或用户有时只有一个想法、观察或疑问，还写不出目标，例如「这个函数看起来有并发问题」。它不满足任务的要求，但也不该丢掉。这类内容不进任务板，作为待分诊项交给 owner leader。leader 分诊后要么补全目标和验收标准建成任务，要么丢弃。待分诊项不能被认领，不能申请租约，不产生记忆。

**结果**

- 进入 `done` 前必须填 `outcome`：逐条对照验收标准，给出是否满足和证据。
- 有标准未满足的任务不能进入 `done`。要么继续做，要么由 owner leader 修改验收标准并记录理由，要么拆出后续任务。
- 结果由 reviewer 对照验收标准核对。只有每条验收标准都绑定了检查的任务才能跳过审查，由检查结果自动对照；有任何一条没绑定的，不能跳过。

**无效任务**

任务在任何阶段被发现本身不成立时，标记为 `invalid`，而不是当作完成或悄悄关掉。

| 原因 | 含义 |
|---|---|
| `false_premise` | 前提不成立：要修的 bug 不存在、对代码现状的假设是错的 |
| `no_goal` | 目标或验收标准无法确定，补不出来 |
| `duplicate` | 和另一个任务是同一件事 |
| `obsolete` | 创建时成立，后来被其他改动解决或不再需要 |
| `infeasible` | 在当前约束下做不到 |

`invalid` 和 `cancelled` 分开：前者是任务本身有问题，后者是任务没问题但决定不做。只有前者需要防止污染记忆。

流程：

1. **核实前提是 planning 的第一步**。agent 先逐条核实 `premises`，再做方案。大多数无效任务应该在这里被发现，此时还没有租约，成本最低。
2. 任何 agent 在任何阶段都可以**提议**判定无效，必须附原因和证据。
3. 由 owner leader 或用户**确认**。提议的 agent 自己不能确认，避免把「做不下去」当成「任务无效」。
4. 确认后：
   - 已有的未提交改动存成变更集归档，路径还原，租约释放（复用 5.6 的搁置流程，但不再恢复）。
   - 已经落地的提交不自动回滚，由 leader 决定是否建一个回退任务。
   - 显式依赖它的任务交给 leader 重新分诊，不自动判为无效。
   - 它产生的记忆按 9.6 处理。
5. 事后发现一个已经 `done` 的任务前提是错的，同样可以追溯标记为无效，记忆处理相同。

`no_goal` 和 `false_premise` 如果反复来自同一个来源（某个 leader 的拆分、某类用户请求），系统统计后提示，这通常说明拆任务的环节需要调整。

## 5. 调度

### 5.1 重叠判定

提交方案时，新任务与所有未完成任务两两比较：

| A 和 B 的关系 | 处理 |
|---|---|
| 无重叠 | 并行 |
| `writes` 或 `creates` 相交 | 加顺序边 |
| A 的 `changes` 命中 B 的 `dependsOn` | 加顺序边；先完成的一方结束后，另一方复核方案 |
| 双方 `changes` 相交 | 加顺序边，并提示 leader 考虑合并 |

**路径怎样算相交**

- 两个具体路径：相同才相交。
- 目录前缀和具体路径：路径在前缀之下就相交，不管它来自对方的 `writes` 还是 `creates`。
- 两个目录前缀：一个包含另一个就相交。

所以 `creates` 尽量写具体路径。两个任务往同一个目录各加一个文件，写了具体路径就可以并行，只写目录前缀就会被排成先后。前缀只在文件名确实定不下来时用（如迁移文件、生成的代码）。

后两条规则依赖接口引用的定义（第 12 节未决问题 1）。在它确定之前只启用路径规则，接口上的先后由 leader 用显式依赖表达。

### 5.2 顺序

按以下优先顺序决定谁先：

1. 已在执行的先完成，不抢占。
2. leader 显式指定的依赖。
3. P 级高的先。
4. 批准时间早的先。

配套规则：

- **成环**：说明拆分不对，交给 leader 合并或重拆，调度器不自己解。
- **复核**：前序任务改动了后序任务的 `writes` 或 `dependsOn` 时，后序任务回到 `planning` 做一次轻量复核。
- **优先级反转**：P0 被执行中的低优先级任务挡住时，后者临时继承 P0 的优先级，优先获得执行资源和审查。

### 5.3 租约

- 进入 `in_progress` 时获取，落地后释放。读不受限，但读到别的任务租约内的文件时会收到提示（5.7）。
- 申请失败立即返回并告知持有者，不允许持有时等待，因此不会死锁。
- **独占的范围是 project**：同一个带仓库前缀的路径，同一时刻只能被一个任务持有，不论它在哪个 workspace。租约记录它所在的 workspace，拦截和对账由那台机器的 daemon 执行。这样两个 workspace 里的任务各自扩租也不会撞到同一个文件。

**执行中扩大租约**

| 目标文件的状态 | 处理 |
|---|---|
| 无人持有也无人预约 | 批准 |
| 被排队中的任务预约 | 批准；该任务加一条顺序边并在轮到时复核 |
| 被执行中的任务持有 | 拒绝 |

被拒后二选一：新建后续任务排在持有者之后，自己先收尾；或进入 `paused`（已持有的租约按 5.6 处理）。默认不抢占。只有 leader 能为 P0 强制抢占，做法是对被抢占方执行 5.6 的搁置流程，并要求它留下交接记录。

被抢占的任务在批内时，先按 5.5 截断：已完成的前缀验证并落地之后 P0 才开工，否则 P0 的基线是一段没验证过的批前缀，自己落不了地。前缀验证不过时交给 leader：等它修好，或者把整批在这些路径上的检查点一起搁置。

**热点文件**

lockfile、`package.json`、路由注册表、i18n 文件、迁移目录等几乎每个任务都会碰。在项目配置中列出，只发短租约，不计入任务间的重叠判定。

短租约覆盖「改、验证、提交」整段：改动按检查映射验证过才提交，不能改完就提交。否则没验证过的片段会进主线，之后所有沙箱的基线都带着它，任务后来失败或被判无效时也收不回来。按改动能否独立成立分两种：

- **能独立成立的**（加一个依赖、加一批还没人用的 i18n key）：随时可以做，作为一个单独的小提交验证并落地，然后释放。任务的其余部分在它之上继续。
- **要和任务的其他改动一起才成立的**（路由表指向新的处理函数、导出表加上新模块）：留到任务收尾时做，和任务的变更集一起验证、一起落地。

持有短租约期间别的任务改不了这个文件，所以第二种要等任务的其他工作都完成之后再申请。

### 5.4 运行中修改任务

- 调度器和 leader 可以随时修改、暂停、取消、改派任务，所有操作都是事件。
- 指令在工具调用边界注入到 agent。
- 取消或改派时，agent 留下可接续的状态：已改的文件、未完成的步骤、当前判断。

### 5.5 批

- 顺序边连成的一个连通分量是一批。
- 批开始执行后封批，新来的重叠任务进下一批。
- 批过大时提示 leader 拆分，或中途加一次前缀验证。

**批在共享目录里怎么运作**

- **检查点不切分支**。同一个工作目录里可能有多个批和不成批的任务同时在做，`HEAD` 不能动。daemon 用任务的变更集直接在批分支上造一个提交（基于批分支的上一个提交），工作目录和 `HEAD` 都不变。检查点按任务完成的先后排成一条线。
- **路径由批持有**。批内任务打完检查点后进入 `verifying` 等批验证，它的路径不释放给批外，直接交给批内的后序任务。批落地后整批的路径一起释放。
- **批内任务的基线是批的前缀**，不是主线：后序任务在工作目录里看到的就是前序任务改完的文件。它的变更集的 `baseHash` 取自上一个检查点。
- **成员暂停时截断**。批内某个任务暂停超过宽限时间时，它之前已完成的前缀单独做批验证并落地，批从它这里截断，它和后面的任务组成新的一批。否则一个任务等用户，整批已完成的工作都落不了地。

### 5.6 暂停任务的租约处理

暂停的任务不能无限期占着文件。规范的让路方式是**搁置**：把任务改过的文件原样拷出保存，把它的路径还原，释放租约。是否搁置、何时搁置由用户的偏好决定。

**偏好**

| 偏好 | 行为 |
|---|---|
| `hold` | 一直持有租约，直到任务恢复 |
| `shelve_on_contention` | 平时持有；有其他任务在等这些路径时才搁置。可设宽限时间，短暂的暂停不触发 |
| `shelve_after` | 暂停超过设定时长后搁置，不管有没有人在等 |
| `shelve` | 一暂停就搁置 |

- 可以按项目、按 P 级、按暂停原因、按单个任务设置，越具体的优先。
- 用户和 owner leader 可以随时对某个暂停的任务手动搁置或取消搁置。

**搁置流程**（由 daemon 执行，不需要 agent 或模型）

1. 把任务改过的文件原样拷出，连同清单存成变更集（7.1），记录基线。删除的文件只记在清单里。
2. 核对副本的哈希和工作目录里的文件一致，防止拷贝期间文件又被写入。不一致则重拷。
3. 把这些路径还原到任务的基线，删除任务新建的文件。不成批的任务，基线就是 `HEAD`；批内的任务是批分支上的上一个检查点（5.5）。
4. 释放租约，写入 `shelf`。任务仍是 `paused`。
5. 重新排序：因 `write_overlap` 排在它后面的任务可以先执行，对应的顺序边反转。

**恢复流程**

没有搁置的任务，暂停原因消除后直接回到暂停前的状态（`pausedFrom`）。已搁置的任务：

1. 暂停原因消除后，任务回到 `queued`，按 5.2 的规则重新排队。它已经不算「在执行」，不享有不被抢占的地位，但保留原来的批准时间。
2. 轮到它时重新获取租约，把变更集放回工作目录。
3. 按路径是否在搁置期间被改过分三种情况：

| 情况 | 处理 |
|---|---|
| 路径没变（哈希等于 `baseHash`） | 直接拷回，从断点继续 |
| 路径变了，能三方合并（基线、副本、当前文件） | 合并后，agent 先复核方案和合并结果，再继续 |
| 合并有冲突 | 回到 `planning`，变更集作为参考材料交给 agent，按当前代码重做方案 |

**代价**

搁置是整个系统里唯一会重新引入合并冲突的地方：让别人先改了同一批文件，恢复时就可能要重新对齐。`hold` 的代价是别人等，`shelve` 的代价是自己可能返工。所以这是偏好而不是固定规则。

**各暂停原因下能否搁置**

| 原因 | 能否搁置 | 说明 |
|---|---|---|
| `needs_input`、`user` | 能 | 等待时间不可预期，最适合搁置 |
| `lease_denied` | 能 | 自己在等别人的租约，同时占着的文件可以先让出来 |
| `agent_lost` | 能 | 工作目录完好，daemon 可以独立完成 |
| `provider_outage` | 能，但通常没必要 | 冻结期间没有会话能利用让出来的路径；默认等恢复后再按偏好计时 |
| `machine_unreachable` | 不能 | daemon 连不上，无法操作工作目录；租约按 13.6 保留 |

**不适用或有特殊处理的情况**

- **依赖关系不因搁置而解除**。后续任务如果依赖这个任务的产出（`explicit` 或 `interface` 边），搁置后它仍然要等。搁置只为单纯写重叠的任务让路。
- **批内的任务**：已提交到批分支的检查点保留，只搁置未提交的部分，路径还原到上一个检查点。搁置超过宽限时间时，批按 5.5 截断。
- **在任务目录或 worktree 里工作的任务**（第 1 级做法 B、第 2 级）：共享目录上没有需要还原的改动，搁置就是保留目录并释放租约。
- **不在变更集里的状态**：被忽略的构建产物、本地数据库等不会被保存和还原。恢复后需要重新构建。

### 5.7 读取提示

读不受租约限制，但 agent 读到的内容可能正在被别的任务修改。读取涉及其他任务的文件或模块时，系统要告诉它。

**触发**

| 情况 | 提示 |
|---|---|
| 读的文件在另一个执行中或已暂停任务的租约内 | 文件级提示 |
| 读的文件被一个排队中的任务预约 | 文件级提示，说明尚未开始改 |
| 读的文件所在模块有其他进行中的任务，且该任务声明要改接口（`changes`） | 模块级提示，列出要改的接口 |

**内容**

- 是哪个任务：编号、标题、状态。
- 它打算改什么：方案摘要和 `changes` 里的接口。
- 你现在看到的是什么：
  - 共享目录里：可能是改到一半的内容。
  - 任务目录里：是基线版本，对方的改动还没有落地，落地后这个文件会变。
- 建议：不要把这个文件当前的内容当作稳定事实。如果本任务依赖它，在影响面的 `dependsOn` 里声明，由调度器排序。

**规则**

- 只提示，不阻止读取。
- 每个会话对每个（文件，任务）只提示一次，模块级提示每个（模块，任务）一次，避免刷屏。
- **对方落地后再通知一次**：「你之前读过的某文件已更新」，agent 据此决定是否重读。这一条比首次提示更重要，否则 agent 会一直拿着旧内容工作。
- planning 阶段读到带提示的文件时，方案里要写明是否依赖它。调度器据此加顺序边或在对方完成后触发复核（5.2）。
- 通过 Bash 读取（`cat`、`grep`）无法逐文件识别，由模块级提示和落地通知覆盖。

## 6. 隔离

`git worktree` 共享对象库，本身不是重新 clone。真正的成本是检出全部文件、安装依赖和冷构建，所以按需使用。

| 级别 | 做法 | 适用 |
|---|---|---|
| 0 | 在共享目录原地工作和验证 | 文档、配置；或任务所在模块及其依赖上没有别人的活跃租约 |
| 1 | 有两种做法，按 project 或任务选择（见下）：A. 在共享目录工作，验证在稀疏沙箱里进行；B. 在任务目录（整仓的写时复制克隆）里工作和验证，结束时只收回租约路径上的文件 | 普通隔离任务 |
| 2 | 完整 worktree，agent 直接在里面工作 | 跨模块重构、高风险试验 |

- 级别由调度器在批准时根据影响面和测试范围决定，leader 可以改。
- 第 0 级之所以可行，是因为租约表让调度器确切知道哪些路径正在被改。
- 第 2 级的任务仍在主 workspace 上持有租约，合并回来时没有冲突。所以 worktree 绕不过租约：P0 热修要改的文件正被别的任务持有时，只有两条路，等对方做完，或由 leader 强制抢占（5.3）。
- 每个 workspace 维护一个沙箱池，循环复用并保留缓存。
- **被忽略的目录不在租约内**。共享目录里的依赖目录、构建产物和缓存是所有任务共用的，一个任务重装依赖或重新构建，会影响别人正在跑的测试。所以要改依赖的任务不在共享目录里做，用做法 B 或第 2 级。

**共享目录也是用户自己的检出**

workspace 的检出不是 tcasd 专用的，用户和 IDE 可以直接在里面改文件，不需要租约。由此有几条规则：

- **用户的改动不还原**。不在任何租约内的改动只上报，不动它（见下面的监听对账）。
- **用户改了某个任务租约内的文件**：不还原，通知持有任务重读。这处改动会随该任务的变更集一起验证和落地。
- **落地只提交租约内的路径**，不碰用户未提交的改动和暂存区。
- **任务目录和沙箱从基线建立**：克隆之后把被跟踪的文件还原到基线，用户未提交的改动和别的任务改到一半的文件不会带进去。
- **原地验证会看到用户未提交的改动**。这类改动落在检查的输入范围内时（7.3），第 0 级任务的验证改到沙箱里做。
- **用户可以在这份检出里提交自己的改动，但不要切换分支、变基或改写历史**：其他任务改到一半的文件都在这个工作目录里。daemon 发现当前分支变了，就冻结这个 workspace 的派发和落地并通知用户。

**第 1 级的做法 B：任务目录**

每个任务一个目录，是共享目录的写时复制克隆（macOS 上 APFS 克隆，Linux 上 reflink 或 overlayfs），依赖目录和构建缓存一起带过来。worker 在里面工作、构建和测试，看到的是基线加自己的改动。

- **收回**：任务结束时 daemon 只把租约路径上的文件收成变更集（7.1），目录里的其他改动丢弃。
- **验证**：直接在任务目录里跑，不需要另建沙箱。
- **搁置**：目录保留，释放租约即可，不需要拷出和还原。
- **基线同步**：别人落地的改动不会自动出现。daemon 在两个时机把非租约文件从主线同步进来：送验证之前，以及本任务依赖的任务或接口落地时。路径独占，所以不会和本任务的改动冲突。不在每次工具调用的间隙同步：后台进程（监听式构建、开发服务器）正在读这些文件，依赖清单一变依赖目录也跟着过期。同步带来依赖清单变化时，daemon 在任务目录里重装依赖。
- **不适用的情况**：文件系统不支持写时复制，或克隆耗时不可接受的大仓库，用做法 A。

只拷租约文件而不是整仓不可行：worker 还要读其余代码、跑类型检查和测试，需要完整的目录树。

**无租约写入在所有级别都要阻止**

任务目录只是多一层保护，不替代拦截。即使越界的写入最终不会被收回，也不能放任：

- agent 会以为改动生效了，并在此基础上继续做，白费工作，还会得出错误的验证结果（测试在一个含有越界改动的目录里通过）。
- 越界本身说明影响面估错了，必须让调度器知道，走扩大租约的流程（5.3）。

所以在任何级别下：编辑工具由 `PreToolUse` 按租约拒绝；Bash 由写权限沙箱或监听对账处理（见下）。任务目录里的越界 Bash 写入同样被对账发现并上报；任务目录只有这一个任务在用，用户不在里面改，所以可以直接还原。

**Bash 逃逸**

`sed -i`、formatter、codegen 等会绕过编辑工具的拦截，解析命令来做事前拦截也做不全。有两种手段，优先用第一种。

*写权限沙箱（首选）*：用 harness 自带的系统级沙箱限制 Bash 进程的写权限，只允许写该任务的租约路径和被 git 忽略的目录。这是事前阻止，没有归属和回滚问题，运行时开销接近零。忽略规则是模式，不是路径，不能直接写进放行列表：daemon 启动会话时把它展开成仓库里实际存在的目录，再加上工具链要写的仓库外缓存和临时目录（由项目配置列出）。这份列表在真实仓库上够不够用还没有测（10.3）。实测结果见 10.4：Codex 可以精确到单个文件；Claude Code 可以，但会话的工作目录必须放在仓库之外；agy 不适合。沙箱不可用或未通过实测的 harness 用下面的监听对账。

*监听对账（兜底，也用于不支持沙箱的 harness）*：

- daemon 用系统的文件事件（FSEvents、inotify）持续收集变化的路径，不扫描工作目录。成本和改动的文件数成正比，和仓库大小无关。
- 被 git 忽略的路径直接过滤。
- 只在 Bash 调用结束后对账：把调用期间变化的路径和租约表比较，是一次集合查询，不读文件内容。
- 这套监听和进行中快照（13.2）、搁置校验（5.6）共用。
- 文件事件积压过多时系统会丢事件，并给出溢出信号。daemon 收到后用 git 对整个工作目录补扫一次。收集变更集时也把租约路径和基线比对一遍（7.1），漏一个事件不至于少提交一个文件。

归属判断（监听只知道文件变了，不知道是谁改的）：

| 变化的路径 | 判断 |
|---|---|
| 在某任务的租约内，该任务当时有工具调用在跑，且没有别的会话同时在跑 Bash | 视为它自己改的，放过 |
| 在某任务的租约内，该任务当时有工具调用在跑，但别的会话同时也在跑 Bash | 归属不确定：不还原，标记这个文件，持有租约的任务在送验证前确认这处改动是不是自己的 |
| 在某任务的租约内，该任务当时没有动作，有别的会话在跑 Bash | 越界，归到当时在跑 Bash 的会话 |
| 在某任务的租约内，该任务当时没有动作，也没有会话在跑 Bash | 用户改的：不还原，通知持有任务重读 |
| 不在任何租约内 | 可能是用户，也可能是某个会话的 Bash，无法区分：不还原，只上报 |

「别的会话」不包括有写权限沙箱的会话，它们写不到自己的租约之外。

这些判断都是按时间窗口推断的。同时有多个会话在跑 Bash 时无法区分是哪一个，全部通知并上报 owner leader；用户恰好在同一时刻改了别的任务租约内的文件，也会被算到在跑 Bash 的会话头上。所以任何还原之前都先存一份（见下）。归属不确定的情况一多，说明这个 workspace 不适合在共享目录里并发。所以 Bash 没有被沙箱收窄的会话（沙箱不能收窄的 harness，或 Claude Code 用仓库内工作目录时），在同一个 workspace 里有其他会话并发时，默认在任务目录（做法 B）里工作：每个目录只有一个任务，不需要靠时间窗口猜归属。用户可以改回共享目录，代价是上面的不确定。

越界改动的回滚：

- 还原之前先把要被还原的内容存成变更集，挂在这次越界的事件上。归属判断错了，或者这处改动其实有用，可以找回来。
- 不在任何租约内的路径不还原，因为这份检出用户也在用，无法确定是谁改的。通知当时在跑 Bash 的会话：是它改的，就自己撤销或申请扩租。仍然留着的列给用户处理。这类改动不在任何变更集里，不会被提交。代价是 agent 越界写到无租约路径时不会被自动清掉，所以事前阻止（沙箱或任务目录）比对账更重要。
- 别人租约内的路径不能还原到 `HEAD`，只能还原到对方最近一次快照，可能丢掉快照之后的少量改动，同时通知双方。

## 7. 验证

### 7.1 变更集

任务的工作以**变更集**的形式保存和传递：改动过的文件的完整副本，加一份清单。不生成 patch。

```ts
interface ChangeSet {
  id: string
  task: TaskId
  base: Snapshot              // 这些文件是基于哪个基线改的
  files: {
    path: string              // 带仓库前缀
    status: 'added' | 'modified' | 'deleted'
    baseHash?: string         // 基线上该文件的哈希，新增文件没有
    hash?: string             // 副本的哈希，删除的文件没有
    mode: string              // 可执行位、符号链接
  }[]
}
```

- **哪些文件变了**来自 daemon 的文件监听（第 6 节），平时不需要扫描或计算 diff。收集时用 git 把租约路径和基线比对一遍作为核对，范围只有租约路径，成本很小。
- **副本是原样拷贝**，不存在「能否还原」的问题，所以不需要应用后再比对的校验步骤。二进制文件同样适用。
- **diff 按需生成**：审查和二分时，用基线和副本现算。它只是展示用的视图，不是存储格式。
- **覆盖的条件**：把副本放到某棵树上时，目标文件的哈希等于 `baseHash` 才直接覆盖。不等说明这个文件在别处被改过，改为三方合并（基线、副本、当前文件）。任务持有租约期间这个条件必然成立，只有搁置后恢复时才可能不成立。
- 路径独占，所以不同任务的变更集互不相交，可以任意叠加。

验证流程：

1. agent 通过 MCP 声明任务完成，daemon 按清单收集变更集。会话的一轮结束不算完成（10.2）。
2. 沙箱检出到**验证时刻的主线**，不是变更集的 `base`，把副本覆盖上去，按 7.3 跑检查。租约保证这些路径在主线上没被别人改过，所以覆盖条件必然成立。在任务目录里工作的任务（第 6 节做法 B）先同步基线，然后直接在任务目录里跑。第 0 级的任务直接在共享目录里跑，条件见第 6 节。
3. 验证失败回到 `in_progress`，租约不放。通过后进入 `review`，可跳过审查的任务直接到下一步。
4. 审查通过后落地：只提交租约内的路径，然后释放租约。审查不通过回到 `in_progress`。

落地的规则：

- **审查在提交之前**。代价是租约要持有到审查结束，所以审查要快：reviewer 是按需启动的一次性会话，等待审查的任务优先分配。
- **每个仓库的落地串行**，一次一个任务或一批。
- **落地前主线又前进了**（验证和审查期间别的任务落了地）：新落地的文件不在本次检查的输入范围内（7.3），直接落地；在范围内，重跑受影响的检查，其余的命中缓存。这样落到主线上的组合都是验证过的。

开发过程中，agent 调用「验证我当前的改动」在沙箱里跑，而不是在共享目录里跑完整测试。共享目录里只允许跑不依赖其他模块的窄范围测试。变更集加基线可以发到另一台机器上验证。

### 7.2 分级

| 级 | 内容 | 触发 |
|---|---|---|
| 1 | 静态检查：路径和接口重叠 | 批准时 |
| 2 | 模块内：类型检查和测试 | 按需，见 7.3 |
| 3 | 受影响范围：沿模块依赖图反向找依赖方，只跑它们的测试 | 按需，见 7.3 |
| 4 | 批验证 | 一批全部完成 |
| 5 | 集成验证：主线最新状态的完整测试 | 最终手段，见下 |

第 3 级需要一份模块依赖图，从 import 或构建工具推导，并由记忆系统补充隐藏依赖。

级别是上限，不是默认动作。每个变更集实际跑什么由 7.3 决定。

### 7.3 按需验证

**每个变更集只跑它的改动能影响到的检查。** 改一个 i18n 文件不应该触发 `pnpm build`。

**检查映射**（项目级配置）：路径规则对应到要跑的检查，调度器按变更集清单里的文件求并集。

```yaml
checks:
  - paths: ["locales/**"]
    run: [i18n-keys]              # 只校验格式和各语言 key 是否齐全
  - paths: ["docs/**", "**/*.md"]
    run: []                       # 不验证
  - paths: ["packages/ui/src/**"]
    run: [typecheck:ui, test:ui:affected]
  - paths: ["package.json", "pnpm-lock.yaml", "tsconfig*.json", "vite.config.*"]
    run: [install, build, test:all]   # 构建配置才跑完整构建
  - default: [typecheck:module, test:module]
```

规则：

- **未匹配的路径走 `default`**，取保守的一档。漏配置的后果是多跑，不是漏验。
- **测试也按受影响范围选**：能用构建工具或测试框架的依赖分析（如按改动文件选测试）就用，不能的才退到整个模块。
- **结果缓存**：以（检查，输入文件哈希）为键。输入没变就复用上次结果，重试和复核不重复跑。输入是这个检查会读到的全部文件，不只是改动的文件：能从构建工具拿到依赖闭包的用闭包，拿不到的用整个模块加它依赖的模块。只按改动的文件算会错误命中，例如类型检查的结果取决于它引用的所有文件。
- **向上扩大由证据触发**：只有改动涉及 `changes` 里声明的接口，或记忆里记录了隐藏依赖，才扩到第 3 级的依赖方测试。
- **映射会被修正**：集成验证抓到某类路径漏验时，系统提议收紧对应规则，由用户确认。
- agent 开发过程中的「验证我当前的改动」走同一套映射，不能自行指定跑完整构建。

批验证和集成验证同样按改动的并集选检查，只是范围是整批或整个区间。

### 7.4 批验证

- 批内按顺序执行，每个任务提交一个检查点到批分支（做法见 5.5），不单独做完整验证。
- 全部完成后，在沙箱里验证 `验证时刻的主线 + 整批`：检查由 daemon 按映射跑，需要判断的部分交给 tester。reviewer 看整批的合并 diff。
- 失败时按前缀二分（主线+A，主线+A+B……）定位到引入问题的任务。
- **修复加在批尾，不回到原位重做**。后面的任务已经在同一批文件上继续改了，退不回去。引入问题的任务回到 `in_progress`，在批的当前末端上修，修完再打一个检查点，整批重新验证。
- 批验证通过后才落到主线，检查点按顺序提交。验证过的是每批的末端，批内的中间检查点没有单独验证：集成验证二分时先以批为单位，再在批内按前缀二分。

### 7.5 集成验证

只在以下时机触发：

- 一个任务组或里程碑完成、发布之前。
- 第 3 级发现了未声明的依赖方，说明影响面不可信。
- 机器空闲时。

失败时在上次通过之后落地的提交里二分，给找到的任务补顺序边并退回，同时把隐藏依赖写入记忆。

代价：两次集成验证之间主线可能带着未发现的语义冲突，间隔越长二分范围越大。间隔是项目级配置。

## 8. Project、workspace 与多仓库

### 8.1 多机器

- 每台机器一个 daemon，主动连到控制面，不需要开放端口。
- 用户通过 UI 或 CLI 远程查看任务板、和 leader 对话、干预任务。
- 验证任务可以跨机器派发。

### 8.2 把任务派到哪个 workspace

任务属于 project，workspace 是派发时分配的执行位置。路径的独占在 project 范围内生效（5.3），但两个 workspace 之间只能通过 git 同步：一边落地的改动要推送、另一边拉取之后才看得见。所以派发按以下规则：

1. **workspace 必须含有任务影响面涉及的全部仓库**。
2. **有写重叠或依赖的任务派到同一个 workspace**，由租约和顺序边处理。
3. 做不到第 2 条时（机器不够、仓库只在别处有），允许跨 workspace 排序，但条件更严：前序任务必须已经落地并推送，后序任务所在的 workspace 拉取之后才能开工。
4. 互不相交的任务可以自由分散到不同 workspace，这是多机器真正带来并行度的地方。
5. 其余按亲和度和负载选择。

两个 workspace 各自落地会让同一个仓库的主线分叉。路径独占，所以变基没有文本冲突，由 daemon 在推送前完成；拉取进来的提交也碰不到本机任务正在改的文件。变基后的组合没有一起验证过，由集成验证覆盖（7.5）。

### 8.3 多仓库

一个 project 可以包含多个 git 仓库。因为所有路径都带仓库前缀，重叠判定、租约、排序、检查映射、记忆锚点的规则都不变。需要单独处理的是下面几件事。

**基线**

- project 的基线是一个快照：每个仓库各一个 commit。方案基线、搁置基线、验证基线都用快照。
- 事件日志给所有仓库的落地事件一个统一的先后顺序，集成验证失败时就沿这个顺序二分，可以跨仓库定位。

**跨仓库的任务**

- **优先拆开**：每个仓库一个任务，用显式依赖和接口边连起来。提供方（如后端接口、共享包）先落地，使用方后做。大多数跨仓库改动都能这样拆。
- **拆不开的**作为一个任务，影响面跨多个仓库：
  - 仍是一个变更集，清单里的路径带仓库前缀。
  - 验证在一个装有相关仓库的沙箱里一起做，各仓库固定在基线快照上再覆盖变更集。
  - 落地按声明的顺序逐个仓库提交，提供方在前。

**落地**

daemon 按顺序在每个仓库提交，全部完成后才释放租约。操作是幂等的，中途中断就从断点重试。某个仓库提交失败时，任务回到 `in_progress` 继续处理，和验证失败一样，不需要额外的状态。

多个仓库各自发布和部署时的先后兼容属于项目的发布流程，不在本系统范围内。

**仓库之间怎么互相引用**

子模块、包版本、同级目录等方式由 project 配置声明。它决定两件事：沙箱怎么把多个仓库组装到一起，以及一个仓库的改动何时算对另一个仓库「可见」（落地即可见，还是要发版并升级版本号）。后一种情况下，升级版本号本身是使用方仓库里的一个任务。

**配置和记忆**

- 检查映射按仓库写，另有 project 级的跨仓库检查（如接口契约测试），只在改动涉及跨仓库接口时触发。
- 跨仓库的约定最适合记在 `interface` 锚点上，它本来就不属于任何一个仓库的文件。
- 域可以跨仓库，team lead 的域简报和优化范围随之覆盖多个仓库。

## 9. 记忆

以 Obelisk 的思路为基础：原始会话和任务事件日志是主体，只做检索；结论是一层带出处、经批准的缓存；默认不用 LLM 和向量检索。在此之上，把锚点从 session 扩展到代码结构。

### 9.1 结构

```ts
interface Memory {
  id: string
  scope: { kind: 'file' | 'dir' | 'module' | 'interface' | 'task' | 'project', ref: string }
  kind: 'invariant' | 'gotcha' | 'decision' | 'dead_end' | 'how_to_verify'
  body: string
  source: { task: TaskId, session: SessionId, commit: string }
  anchorHash?: string
  status: 'candidate' | 'approved' | 'stale' | 'retired' | 'quarantined'
}
```

`quarantined`：来源任务被判定为无效，记忆被隔离，见 9.6。

### 9.2 写入

- **agent 写**：任务结束时提交候选记忆并指定锚点，默认范围是自己的影响面。只记代码里看不出来的内容：原因、走不通的路、隐含的不变量、验证方法。
- **批准**：候选记忆在来源任务进入 `done` 之前只对该任务自己可见，之后可被检索但带标记。升级为 `approved` 由 owner leader 或用户完成，且要求来源任务已 `done`；reviewer 审 diff 时顺带审记忆。
- **系统写**（不需要批准，来自事件日志）：
  - 集成验证二分出的隐藏依赖，挂到两个模块。
  - 影响面估错的记录，挂到模块。
  - 验证失败的原因和修法，挂到文件或模块。

### 9.3 投递

按锚点推送，不依赖 agent 主动搜索。

| 时机 | 内容 |
|---|---|
| 认领后做方案时 | 影响面涉及的模块和接口层记忆，加相关的 `dead_end` |
| 首次读或改某个文件 | 该文件和所在目录的记忆，每个会话一次 |
| 申请扩大租约 | 新路径上的记忆 |
| reviewer 开始审查 | 涉及路径的 `invariant`，作为检查清单 |

层级向上继承（文件 → 目录 → 模块 → 项目），越具体越优先，有 token 上限，超出部分只给标题。

### 9.4 过期

- 落地的改动碰到某个锚点时，对应记忆标为 `stale`，交给做这次改动的 agent 确认：仍成立、需更新、或作废。
- 改名和移动通过 git 跟踪，锚点跟随。
- `stale` 的记忆仍投递，但标注写入时的提交和此后文件已变。

### 9.5 反馈给调度器

只统计有效任务（`done` 以及进行中的任务）。无效任务的数据不进入下表的任何一项。

| 数据 | 用途 |
|---|---|
| 模块的历史任务实际碰过的文件 | 批准时提示方案可能漏掉的影响面 |
| 隐藏依赖 | 补进模块依赖图，在第 3 级验证拦截 |
| 租约争用历史 | 自动发现热点文件 |
| 原地验证的失败率 | 调整模块的默认隔离级别 |
| 会话的工作历史 | 派任务时的亲和度 |

### 9.6 无效任务与记忆

无效任务里产生的结论建立在错误的前提上。让它们留在记忆里，后来的 agent 会把错误的假设当成事实。

**写入时的限制**

- 候选记忆只有在来源任务进入 `done` 后才能升级为 `approved`。任务还没完成时，它的候选记忆不投递给其他任务。
- 这样大多数无效任务（在 planning 阶段被发现的）根本不会留下已批准的记忆。

**任务被判定无效时**

1. 来源是这个任务的全部记忆（`source.task`）转为 `quarantined`：不投递，不参与默认检索。
2. 系统写入的统计类数据（影响面记录、验证失败、租约争用）同样剔除，不进入 9.5 的反馈。
3. 会话原文和事件日志保留，但带上无效标记。默认检索排除它们，显式指定时才能查到，用于审计和追溯。
4. 已经被其他任务引用过的记忆：记录哪些任务在方案里用到了它，通知这些任务的 owner leader 复核。

**保留一条：为什么无效**

无效任务唯一值得记住的是它无效的原因，这能防止同样的任务被再次创建。

- 判定时生成一条 `dead_end` 记忆，内容是原因和证据，挂到相关的模块或文件上。
- 这条记忆不来自任务里的推理，而来自判定本身，由确认无效的 leader 或用户批准。
- 以后有人在同一模块创建相似的任务或做方案时投递，例如「2026-11 曾有任务要修这个问题，核实后发现现象来自测试数据而不是代码」。

**隔离的记忆可以恢复**

判定有误时，owner leader 或用户可以撤销无效标记，被隔离的记忆恢复原来的状态。任务回到判定前的状态；判定时已经开工的，租约已释放、改动已归档，所以按搁置后的恢复流程走（5.6）：回到 `queued`，轮到时取回归档的变更集。

### 10.2 对设计的影响

**成立的部分**：三个 harness 都能在工具调用前拒绝、注入上下文、阻止结束、无界面运行和续接。第 10 节开头的接入点表在三者上都有对应。租约检查用「每次调用都向 daemon 查询的静态 hook」实现，租约变化不需要改任何配置文件。

**必须两层拦截**：沙箱只管 Bash 及其子进程，编辑工具不在沙箱里。所以编辑类工具靠 `PreToolUse`，Bash 靠沙箱，缺一不可。

**hook 必须自己做到失败即拒绝**：三者默认都不保证 hook 出错时拦截。hook 脚本连不上 daemon、超时或异常时，必须主动返回拒绝。Claude Code 另外设 `onFailure: "block"`。否则 daemon 一挂，租约检查就悄悄失效。

- **hook 根本没跑起来时它没法拒绝**（程序不存在、崩溃、被 harness 超时杀掉）。所以 daemon 另外核对 harness 的事件流：看到一次编辑类工具调用，却没有收到对应的 hook 查询，就暂停这个会话并对账。事件流能否支持这种核对待实测（10.3）。
- **失败即拒绝只用于写入拦截**（`PreToolUse`）。读取提示、上下文注入和 `Stop` 在 daemon 不可用时放行，否则 daemon 一挂，所有会话连结束都结束不了。

**daemon 启动会话的方式**：

- Claude Code：无界面加流式输入输出。不能用 `--bare`，该模式下 hooks 不运行。
- Codex：优先 `app-server`，可以中途追加输入、打断、更换权限 profile。项目级 hook 需要先建立信任，否则不执行。
- agy：`-p` 加流式输入输出。不能用跳过权限检查的启动参数，第三方测试称它会让 `PreToolUse` 不触发。

**各自的注意点**：

- Claude Code：Linux 上 `allowWrite` 指向不存在的路径时无效，影响 `creates` 声明的新目录，需要先建目录。hooks、本地 MCP 服务本身运行在沙箱之外。
- Codex：glob 形式的拒绝规则在部分平台上于沙箱启动时固定，会话中新建的文件可能不受约束。
- agy：没有项目级的 CLI 设置文件，权限规则只能写全局文件，多个会话并行时会互相影响。这使它不适合用沙箱做按任务的写限制，只能靠 hook 加监听对账。

**Stop 的用法要调整**：

- `Stop` 在每一轮结束时都会触发，不等于任务完成。任务完成由 agent 通过 MCP 显式声明，daemon 据此收集变更集并送验证。
- `Stop` 只作兜底：任务还在 `in_progress`，agent 既没有声明完成，也没有提问或留下交接记录时，阻止结束一次并提醒它。
- Claude Code 连续阻止结束最多 8 次。验证耗时长或反复失败时不能一直用 `Stop` 把会话顶住，应该让会话结束，验证结果出来后再续接。

### 10.3 仍需实测

1. Claude Code 的 `allowWrite` 能否精确到单个文件。
2. Claude Code 中途修改可写路径，对通过 `--settings` 传入的配置是否生效；Codex 通过 app-server 中途更换 profile 是否生效。
3. Codex 的 `apply_patch` 是否和 shell 命令受同样的可写路径约束。
4. 三者的 hook 在超时和崩溃时的实际行为。
5. agy 的 hooks 在无界面模式下是否触发，以及无终端时输出为空的问题是否还在。
6. Linux（bubblewrap）上重复 10.4 的全部用例。
7. 在收窄后的沙箱里，对一个真实仓库跑完整的安装、构建和测试，确认可写列表（租约路径、被忽略的目录、仓库外的缓存和临时目录）够用。10.4 只测了临时目录里的读写。
8. 三者的事件流是否包含每一次编辑类工具调用，能否用来核对 hook 确实执行过（10.2）。

### 10.4 Bash 沙箱写权限实测（2026-11-19，macOS）

测试方法：临时目录里建 `leased/` 和 `other/`，在沙箱内分别尝试改写、新建文件，目标是只有 `leased/` 可写。

**Codex CLI 0.166.0**（用 `codex sandbox` 直接跑命令，没有经过模型）

可用的配置：继承内置的只读 profile，再对租约路径放行写。

```toml
[permissions.lease]
extends = ":read-only"

[permissions.lease.filesystem.":workspace_roots"]
"leased" = "write"
```

| 用例 | 结果 |
|---|---|
| 改写、新建 `leased/` 内的文件 | 允许 |
| 改写 `other/` 内的文件、在仓库根新建文件、写仓库之外 | 拒绝 |
| 只放行单个文件 `leased/a.txt` | 该文件可写，同目录其他文件不可写、不可新建 |
| 子进程（`sed -i`、`python3`）写非租约文件 | 拒绝 |
| 放行一个尚不存在的目录 | 可以创建并写入，其他目录不能创建 |
| 可写目录内再设一个只读子目录 | 子目录不可写 |
| 不继承任何内置 profile，只写路径规则 | 命令直接异常退出，无法使用 |

没有测：`apply_patch` 是否受同样约束，会话中途更换 profile。

**Claude Code 2.1.327**（无界面会话，由模型执行一条固定的脚本）

| 配置 | 结果 |
|---|---|
| 工作目录是仓库，`denyWrite` 整个仓库加 `allowWrite` 租约路径 | **全部拒绝**，包括租约路径。拒绝规则优先，不能用来「先禁后放」 |
| 工作目录是仓库，`denyWrite` 列出非租约路径 | 列出的被拒绝，但仓库根和其他未列出的路径仍可写。需要枚举所有非租约路径，不实用 |
| 工作目录是仓库外的一个空目录，`allowWrite` 只列租约路径 | **符合预期**：只有租约路径可写 |

原因是 Claude Code 的工作目录默认整体可写，且无法用规则收窄。所以唯一可行的做法是让会话的工作目录不在仓库里。

**对设计的影响**

- Codex：按任务生成一个 profile，路径直接取自租约，文件级租约也能表达。
- Claude Code 有两种方案，按 project 或按任务选择：

  | 方案 | 做法 | 代价 |
  |---|---|---|
  | 仓库外工作目录 | daemon 为每个会话建一个空的工作目录，仓库通过绝对路径访问，`allowWrite` 列出租约路径 | 仓库里的项目级配置和 `CLAUDE.md` 不会自动加载，要由 daemon 通过 `--settings` 和 `SessionStart` 注入；agent 的所有路径都是绝对路径 |
  | 仓库内工作目录 | 会话照常在仓库里启动，Bash 越界靠监听对账（第 6 节） | 事后发现而不是事前阻止；多个会话同时跑 Bash 时越界归属不确定 |

  两种方案下编辑工具都由 `PreToolUse` 拦截，区别只在 Bash。
- 两者的沙箱都只管 Bash，编辑工具仍然靠 `PreToolUse`（10.2）。

### 10.5 接入方案（提议，待确认）

原则：**各家的差异只留在一层很薄的适配器里，策略全部在 daemon。**

**三个共用部件**

| 部件 | 作用 | 说明 |
|---|---|---|
| 适配器接口 | daemon 用同一组操作驱动任何 harness：启动、发消息、打断、续接、停止、事件流 | 每个 harness 一个实现，并声明自己的能力（能否中途追加、能否打断、沙箱能否收窄） |
| 统一的 hook 程序 | 三家的 hook 配置都指向同一个小程序 | 它只做三件事：把各家的输入归一化，经本机套接字问 daemon，按各家的格式输出。连不上 daemon、超时或出错一律返回拒绝 |
| 统一的 MCP 服务 | agent 主动发起的操作：读任务板、认领、提交方案、扩租、请求验证、声明完成、提问、提交候选记忆 | 三家都支持 MCP，agent 侧的接口完全一致 |

hook 负责系统对 agent 的约束和通知，MCP 负责 agent 对系统的请求，两者不混用。

**各家的通道**

| | 启动和通信 | 配置注入 | Bash 约束 | 中途追加消息 |
|---|---|---|---|---|
| Claude Code | 无界面模式，流式输入输出 | 启动参数传入设置和 MCP 配置，不依赖仓库里的文件 | 沙箱（仓库外工作目录）或监听对账 | 当前工具调用结束后送达 |
| Codex | app-server（JSON-RPC）；不稳定时退到 `exec --json` 加续接 | 启动参数覆盖配置，按任务生成权限 profile；hook 要先建立信任 | 沙箱，按租约生成 profile | 原生支持追加和打断 |
| agy | 无界面模式，流式输入输出 | workspace 下的 hooks 和 MCP 配置文件 | 只能监听对账 | 等一轮结束，或取消后重发 |

**ACP 的位置**：不作为这三家的主通道（原生通道能力更全，steer 在 ACP 里还是非标准扩展）。保留一个通用的 ACP 适配器，用来接入没有专门适配的 harness。

**能力分级**：调度器按适配器声明的能力决定能派什么任务。

| 级别 | 条件 | 可承担 |
|---|---|---|
| 完整 | 有 hooks，沙箱可收窄 | 任何角色和隔离级别 |
| 部分 | 有 hooks，沙箱不可收窄 | 任何角色；Bash 越界靠监听对账，同一个 workspace 有其他会话并发时默认在任务目录里工作（第 6 节） |
| 基本 | 没有 hooks（如纯 ACP 接入） | 只在任务目录（第 6 节做法 B）里做 worker，或做只读的 reviewer |

**leader 会话**用同一套适配器，区别只是权限为只读、会话长期保持，用户的消息由 daemon 转发。

**顺序**：先 Claude Code，再 Codex，agy 最后。每接入一家之前先跑一组固定的验收用例（10.3 的未测项加上：无界面模式下 hook 是否触发、hook 出错时的行为、续接后 hook 和配置是否仍然生效）。

| 4 | 系统写的记忆及其对调度的反馈，无效任务的数据剔除和 `dead_end` 记录 | 调度质量随使用改善，且不被无效任务带偏 |
| 5 | 多机器、远程 UI、跨机器验证、workspace 派发规则、多仓库（跨仓库任务的变更集和按序落地） | |
| 6 | agent 写的记忆、批准流程、过期处理、无效任务记忆的隔离和恢复 | |
| 7 | 第 2 级隔离、集成验证的自动触发和二分 | |

## 12. 已知限制和未决问题

**已知限制**

- **未声明的语义冲突**：双方都没写进影响面的行为依赖，只能靠第 3 级和集成验证发现。
- **沙箱外的共享资源**：端口、本地数据库、模拟器、全局缓存。需要按沙箱分配，或把相关测试标记为串行。
- **大仓库的沙箱成本**：首次依赖安装和冷构建慢，依赖沙箱池和缓存共享的质量。
- **跨 workspace 的同一仓库**：路径独占在 project 范围内生效，但两边的主线靠推送和拉取同步，变基后的组合没有一起验证过，由集成验证覆盖（8.2）。
- **模块划分的质量**决定并行度。划分差的项目会退化成一条串行队列。
- **影响面的准确度**：整个模型依赖 agent 在开工前说得准要改哪些文件。扩租被拒一多，暂停和搁置就成了常态。阶段 0 先测这个数（第 11 节）。
- **预约造成的连带等待**：任务 Q 因为文件 f1 排在一个慢任务之后，同时预约了 f2；只改 f2 的新任务会排到 Q 后面，尽管 f2 空着。见未决问题 18。
- **和用户共用检出**（第 6 节）：agent 越界写到无租约路径时只上报、不还原。用户在这份检出里提交时要只提交自己的文件，`git commit -a` 会把 agent 改到一半的文件一起提交。
- **分支**：租约、基线和落地都只针对每个仓库的默认分支。发布分支上的热修和长期特性分支目前无法表达。

**未决问题**

1. 接口引用（`InterfaceRef`）如何定义和发现：人工声明、从代码提取，还是两者结合。
2. 自动批准的阈值和各模块的默认隔离级别。
3. 集成验证的间隔。
4. 批的大小上限，以及封批后的新任务如何提示用户。
5. 增设 team lead 的信号阈值，以及触发域维护任务的各项阈值。
6. 控制面的部署形态：本机进程、自托管服务，还是两者都支持。
7. 支持哪些 harness，以及没有事前拦截能力的 harness 是否接入。
8. 是否配置备用 provider 或备用 harness，以及故障时自动切换还是等用户决定。
9. 用户输入的默认超时，以及哪些类别的问题默认不允许 leader 代答。
10. 开工后问题的偏好（`pause`、`proceed` 或 `leader`）出厂默认值是哪个，以及不可代答的问题是否无视 `proceed` 和 `leader` 一律暂停等用户。
11. 暂停任务的租约偏好出厂默认值，以及 `shelve_on_contention` 的宽限时间。
12. 验收标准「可检验」由谁把关：控制面只能检查非空和是否绑定了检查，没绑定检查的条目质量需要 leader 在批准方案时判断，是否再加一道检查。
13. 无效任务已落地的提交是否默认建回退任务，还是每次由 leader 决定。
14. Bash 的写权限沙箱：Codex 和 Claude Code 在 macOS 上实测可以收窄到租约路径（10.4），agy 不适合。Claude Code 的「仓库外工作目录」已确定作为可选方案之一，和「仓库内工作目录加监听对账」并列。待定的是哪个做默认，以及 Linux 上的结果。
15. 第 1 级默认用做法 A 还是 B（沙箱不能收窄的 harness 在有并发时已定为 B，见第 6 节）。做法 B 的克隆耗时和基线同步的开销还没有实测，尤其是依赖目录很大的仓库。
16. 仓库之间的引用方式（子模块、包版本、同级目录）各自怎么组装沙箱，先支持哪几种。
17. 同一个系统用户下，对蓄意绕过的防护做到什么强度（3.7）：会话令牌挡得住顺手越权，挡不住 agent 去读 daemon 的进程内存或用户的凭据文件。是否让 daemon 和会话用不同的系统用户运行。
18. 预约是否应该挡住能立刻开工的任务。放行可以消除连带等待，但需要多条路径的任务可能一直凑不齐，要配一条防饿死的规则（如等待超过一定时间后它的预约变成硬性的）。
19. 派生文件（代码生成的产物、测试快照）在开发过程中就要重新生成，收尾时才申请的短租约不适用（5.3）。候选做法：这类文件不发租约，开发时在任务目录或沙箱里生成，落地时由 daemon 在主线上重新生成。
20. 是否支持默认分支以外的分支（发布分支热修、长期特性分支），租约和基线要不要带分支。
21. 批内成员暂停后触发截断的宽限时间（5.5），以及截断出的前缀验证不过时的默认处理。

## 13. 故障与恢复

**前提**：控制面和 daemon 是确定性程序，不调用任何模型。provider 故障或网络抖动可以让从 worker 到 leader 的所有会话同时失效，但任务板、租约表、事件日志和工作目录都还在。恢复的全部依据是这些持久状态，不是任何会话的上下文。

### 13.1 故障类型和判定

daemon 监视每个会话的进程状态、最近一次工具调用时间和 harness 报出的 API 错误，向控制面上报心跳。

| 故障 | 判定 | 影响范围 |
|---|---|---|
| 单个会话失效 | 进程退出，或超过阈值没有任何活动 | 一个任务 |
| provider 故障或限流 | 同一 provider 的多个会话在短时间内报 API 错误或同时停滞 | 该 provider 上的全部会话，可能包括所有 leader |
| daemon 与控制面断连 | 心跳中断，但机器上的会话可能仍在正常工作 | 一台机器 |
| 机器或 daemon 宕机 | 心跳中断且重连后会话已不存在 | 一台机器上的全部任务 |
| 控制面宕机 | daemon 连不上 | 全局的派发和批准 |

区分单个失效和 provider 故障很重要：前者应该换人接手，后者换谁都没用。

### 13.2 通用规则

1. **掉线不直接释放租约**。工作目录里留着改到一半的文件，直接放开租约等于让别人在脏状态上继续。任务进入 `paused` 并记录原因；租约要么继续持有，要么走 5.6 的搁置流程后释放，由用户偏好决定。
2. **进行中快照**。daemon 定期把每个任务改过的文件拷成变更集（纯文件操作，只拷上次快照之后变过的文件，不需要 agent 配合）。会话无论怎么死，工作都不丢。
3. **未完成的任务释放租约只有一种方式**：5.6 的搁置流程（拷出、还原、释放）。之后任何会话都可以从变更集继续。这一步由 daemon 按偏好自动执行或由用户触发，不需要 LLM。
4. **提交、收集变更集、验证由 daemon 执行**，不由 agent 执行。会话在任何时刻死掉都不会留下半个提交，已经开始的验证会照常跑完并记录结果。
5. **所有写操作幂等**，带任务的 `rev` 和事件序号，断线重放不会重复生效。

### 13.3 单个会话失效

1. 任务进入 `paused`（`agent_lost`），租约按 5.6 的偏好处理。
2. 优先**续接**：用 harness 的会话恢复能力重启同一个会话，上下文还在，成本最低。三家都支持按会话 ID 续接（10.1）。续接恢复的是对话，不是文件状态，文件靠进行中快照（13.2）。
3. 续接不了则**交接**：启动新会话，交给它任务的 brief、已批准的方案、影响面、租约路径上当前的 diff、事件日志里的进度和最后一份交接记录。
4. 连续失败超过次数上限后停止重试，上报给 owner leader 或用户。常见原因是任务太大撑爆上下文，应该拆分而不是重试。

`planning` 阶段的认领过期后直接回到 `open`，没有文件需要处理。

### 13.4 Provider 故障或网络不稳定

判定为 provider 级故障后，系统进入**冻结**状态：

- **停止派发**，不启动新会话，不做交接（换会话也连不上）。
- **暂停所有计时器**：认领过期、无活动超时、优先级老化、用户输入的超时。否则恢复时一批任务会因为超时被错误地收回，或者问题在没有 leader 可以代答时到期。
- 受影响的任务标为 `paused`（`provider_outage`），租约和快照保留。
- **不依赖模型的工作继续**：已送出的变更集的验证、缓存命中、批的二分、事件记录。
- 用探测请求按退避间隔检查 provider 是否恢复。

恢复时：

- **分批续接**，不同时拉起全部会话，避免立刻撞上限流。
- 顺序：先 leader，再按 P 级和「是否挡着别人」恢复 worker。
- 每个会话恢复后先收到一份变更摘要：掉线期间任务板上发生了什么、自己的任务是否被改动。

网络不稳定（时断时续）按同样的机制处理，但加一个迟滞：连续稳定一段时间才解除冻结，避免在冻结和恢复之间反复切换。

如果配置了备用 provider 或备用 harness，可以切换过去继续。任务状态与 harness 无关，所以交接可以跨 harness。是否自动切换是未决问题。

### 13.5 Leader 失效

leader 的全部状态都在任务板上，所以它是可替换的。没有 leader 的期间：

- **不需要判断的事照常进行**：自动批准档的任务、排序、租约、验证、已排队任务的开工。
- **需要判断的事进入待办队列**：方案审批、成环的拆分、新任务分诊、扩租被拒后的决定。不超时、不自动通过。
- **超时待 leader 代答的用户输入**保持未答，继续留在用户的待答队列里。
- **偏好为 `leader` 的开工后问题**退回到 `pause`，进入用户的待答队列。
- **逐级接管**：某个 team lead 失效而 PM 可用时，它的待办队列由 PM 接管；PM 也失效时由用户接管。
- **用户可以直接代行 leader**，在 UI 或 CLI 里处理待办队列。这条路径不经过任何模型，所以全部 agent 掉线时系统仍然可操作。
- leader 恢复后从任务板和待办队列重建现场，不依赖之前的对话上下文。

### 13.6 Daemon 与控制面断连

机器上的会话可能还在正常工作，所以不打断它们。

- daemon 用本地缓存的租约表继续做拦截，**已持有的租约照常有效**。
- 需要控制面决定的操作一律**拒绝**：新租约、扩租、认领、提交落地。agent 可以继续在已有租约内工作。
- 事件在本地缓冲，重连后按序号重放。
- 控制面把这台机器标为失联，其任务标为 `paused`（`machine_unreachable`），但不收回租约：那台机器上的会话可能还在改这些文件。路径的独占范围是 project（5.3），所以其他 workspace 里需要这些路径的任务要等。
- 失联超过宽限期后通知用户，由用户决定：
  - 等待。
  - 把尚未开工的任务改派到其他 workspace（它们只有预约，没有租约）。
  - 强制搁置某个任务，让别的 workspace 先做：控制面先释放租约，那台机器重连后 daemon 补做拷出和还原。代价和搁置一样，它的改动按 5.6 的恢复流程处理，可能要三方合并。

### 13.7 机器或 daemon 宕机

- daemon 重启后扫描每个 workspace：对比租约表、最近的快照和工作目录的实际状态，上报差异。
- 状态一致的任务按 13.3 续接或交接。
- 状态不一致（有越界改动，或快照比工作目录新）的任务保持暂停，交给 leader 或用户处理，不自动修复。

### 13.8 控制面宕机

- 各 daemon 按 13.6 的方式降级运行。
- 控制面从事件日志重建任务、租约和排序状态，然后接受 daemon 重放缓冲的事件。
- 需要可靠持久化和备份的数据有两样：
  - **事件日志**。任务、租约、排序都能从它重建。
  - **变更集的文件内容**。搁置的、归档的、送去验证的变更集上传到控制面的变更集库；事件日志里只有它们的编号和清单，内容丢了，搁置的工作就找不回来。
- 进行中快照留在所在机器上，不上传。那台机器的磁盘坏了，丢的是这台机器上未搁置任务的进行中改动。
